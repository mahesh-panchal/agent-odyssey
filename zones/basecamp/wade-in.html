Wade In

Prerequisites: Know Your Gear, and Python 3 for the exercise. Objective: choose how much of your data and your machine to hand over for one task, and start at the lowest step that gets the job done. Time: about 20 minutes. Last verified (docs, not run): Anthropic privacy pages read 2026-11-23 through a summarising tool (research/wade-in.md), Claude Code data usage page read 2026-11-17. Verified: ran the exercise files below on 2026-11-23. The steps and the data table are General practice. Your own data agreement overrides anything here.

The scene

A manager has to write a report from the project database: samples received, milestones still open. They have two worries. The first is where the data goes. The second is a belief, that to use an LLM at all they must let an agent loose on their computer.

The second belief has a gentler answer. Between “never” and “the agent runs my machine” there are several steps, and many useful tasks sit on the lower ones. You may stop at any step. Choosing not to climb is a legitimate decision at every one.

Two dials

Two questions are easy to mix up, and they turn independently.

  1. What leaves your machine? With a hosted model, anything you type, paste or upload is sent to the provider, and so is anything an agent reads. A model running on your own machine (see Adopt the Pet) keeps prompts local. Web or tool calls it makes may still reach out (General practice, not checked in the docs). The Claude Code docs say it sends all prompts and model outputs over the network (read 2026-11-17). For a chat window the same reasoning holds (General practice).
  2. What may the tool do? It may only produce text. It may read files. It may edit files. It may run commands.

A chat window has the lowest second dial and can still carry a whole table to the provider if you paste one. A read-only agent has a low second dial too, and it still sends whatever it reads. Each dial needs its own decision.

The ladder

Step What you do What leaves What the tool can do Good for
0 Write the report yourself nothing nothing Always a valid choice
1 Chat with no data the words you type produce text An outline, wording, how to explain a chart, a checklist for the report
2 Chat with the schema (the table and column names) and a few invented example rows; you run the code it writes those names and the invented rows. Pasting the results back would send those rows too, which is step 3 produce text The numbers in the report: it writes the query (a SQL request that only reads, when it starts with SELECT), you run it
3 A small extract your agreement allows, or a local model on the real data the extract; nothing for a local model produce text Tidying prose, summarising free text
4 A read-only agent on a copy of the data everything it reads read files A folder you have already looked through and know is safe to share
5 An agent that edits and runs commands everything it reads, and whatever it runs may send more change files, run commands Pipeline and code work, with a save point and permission rules

Plan mode (a mode where the agent reads and proposes and does not edit; see Recruit the Beast) belongs to step 4. It limits what the agent does. What is exposed depends on what it reads, and reading sends it. A copy of the data protects the original from edits and is still sent when read.

Three questions before any step

  1. What kind of data is it? The table gives a typical starting point (General practice). Your agreement, your data steward and your institution’s rules decide, and they can be stricter.
  2. Which account will you use? Consumer and organisation accounts have different documented terms, below.
  3. What leaves at this step? Say it in one sentence before you press enter.
Kind of data Typical starting point
Public or already published Any step
Internal and not personal (project names, milestone dates, status) Steps 1 to 3 on an account your organisation allows. Steps 4 to 5 only on an approved account, on a copy
Personal data, including pseudonymised codes (codes that replace names, and still count as personal data) Steps 0 to 2 with no real rows. Higher steps need an approved account and agreement. Ask your data steward (the person at your organisation who looks after data rules)
Controlled or special-category data (health, genetic or other data under extra legal protection or a special agreement) Steps 0 to 2. A local model only if your agreement allows that copy. Anything else only if it says so in writing

Small counts can single people out even when no names are present, so check your policy before pasting results for rare groups (General practice). The Locked Cabinet covers personal data, agreements and keys in more depth.

What the docs say about the chat window

Read 2026-11-23 on Anthropic’s privacy and support pages, through a summarising tool, so re-check the wording on the live page. Sources are in research/wade-in.md.

  • Consumer accounts (Free, Pro, Max) have a setting that lets chats improve the models. The page states no default. With it on, data may be kept, with identifying details removed (de-identified), for up to 5 years. This page gives no number for it being off, only “as long as reasonably necessary”. (The Claude Code page gives 30 days for Claude Code sessions.)
  • Commercial accounts (such as Claude for Work and the API): the pages say inputs and outputs are not used for training, with exceptions such as feedback you send. They are deleted from the provider’s storage within 30 days by default, and longer for content flagged for a policy violation or when a longer-retention service is used.
  • Consumer accounts, after you delete a chat: it leaves the provider’s storage within 30 days.
  • Incognito chats are not used for training, and are still kept for 30 days by default, longer if an Enterprise organisation sets a longer period, and may be kept longer if flagged for a policy violation.
  • People reading chats: for consumer accounts, Anthropic staff cannot read conversations by default, unless you share them as feedback. Designated members of a Trust and Safety team may access that data on a need-to-know basis.
  • Uploaded files: we found no page that treats files differently from typed text, so treat a file like pasted text (General practice).
  • Other providers’ chat tools have their own terms. Read those for the tool you use.
  • Screenshots, images, chat memory, connectors and browsing features are data too (General practice). Not checked: how each is handled.
  • To find out which account you are on, look at the plan shown in your account settings, and ask your administrator if your organisation provides it. The training setting for consumer accounts sits in the privacy settings (Not checked: the exact menu names change).

Hands-on: the report, without handing over the data

Files: make_db.py, run_query.py, report-query.sql and check-samples.sql. Save all four into an empty folder. Every row is invented. No LLM is called.

  1. Build the mock database and the schema text. Run python3 make_db.py (or python, depending on your machine). It writes mock.db and schema-only.txt. Open the text file: table and column names, no rows. That is all that would go into a chat window at step 2. Look at the column names. participant_code and notes hint at what the real database holds, so decide whether even the names are fine to send.

  2. The prompt you would send.

    I have a SQLite database with this schema:
<paste schema-only.txt>
Write one read-only SQL query that gives, for each project, the number of
samples received and the number of open milestones (done = 0).
I will run it myself and check the numbers. Do not ask me to paste any rows.

  3. The reply. report-query.sql stands in for what a model sent back. Read it before you run it: is it a single SELECT, and does it touch only the tables you expect? Then run python3 run_query.py report-query.sql. The script opens the database read-only, so a DELETE fails with “attempt to write a readonly database” (verified by running it).

  4. Check it against something the model did not write. Run python3 run_query.py check-samples.sql and compare:

    Project Model’s query: samples Your check: samples Model’s query: open milestones Open milestones in the data
    Heron 22 11 22 2
    Kelp 28 14 28 2
    Vega 34 17 34 2

    The query ran without an error, and its numbers are wrong. If you cannot run Python, read the table as a worked example, or ask a colleague to run it with you. Each project has two open milestones, and the query pairs every sample with every open milestone, so each sample is counted twice, and the milestone column repeats the same inflated number. Ask the model (or edit the query yourself) to fix it, then run both again until you get 11 and 2 for Heron.

The data stayed on your machine all the way through. Only the schema and the query text travelled. The check still mattered: running without an error and being right are separate questions, which is the lesson of Spot the Mirage.

Climbing, if and when you want to

  • Move up a step when you have a task the lower step could not do, and a sentence saying what leaves.
  • Before steps 4 and 5, work on a copy of the data, set a save point (Save Point) and add permission rules (Grow the Carapace, the quest on limiting what an agent may do).
  • For sensitive data you may prefer to stay on a local model (Adopt the Pet), when your agreement allows that copy.
  • If you have already pasted something you should not have, stop and tell your data steward. The Locked Cabinet explains what a session keeps behind.
  • A one-line message for your data steward: “For a report from the project database I want to use [tool, account type] at step [n]. What leaves is [what]. Is that allowed for [data kind]?”
  • When you are ready for an agent, Recruit the Beast installs one and starts it in plan mode.
