Plan Before You Edit

  • Goal: you will ask an agent for a plan before it edits, review that plan like a reviewer, and know what a plan can and cannot guarantee.
  • Before you start: Write the Brief. The exercise uses mock files on your laptop and runs no model.
  • Time: about 20 minutes.

Why plan first

A wrong plan costs you a paragraph to read and reject. A wrong 400-line diff (the list of lines a change added and removed) costs you the time to review it, and the longer it is, the more likely you approve something you did not understand. A plan is the cheapest piece to ask for first. Ask for small pieces, and accept only as much output as you can honestly review.

Use plan mode for changes you want to review before they touch disk.

How: plan mode

Words used below:

  • Session: one conversation with the agent.
  • Shell commands: commands you would type in a terminal, such as ls or git status.
  • Context: everything the model can see in the session.
  • Subagent: a helper with its own context window; only its summary comes back.
  • Deny rule: a rule that blocks an action in every mode.
  • Auto mode: a mode where a background check decides what runs without a prompt.
  • Bypass permissions: a startup option (--dangerously-skip-permissions) that turns most prompts off.
  • -p: runs one command with no chat (non-interactive mode).
  • Agent SDK: a library for building your own agent programs.
  • Claude Code
  • OpenCode + Ollama

In Claude Code, plan mode is a permission mode: a setting for what the agent may do without asking you. In plan mode the agent reads files, may run shell commands to explore, and writes a plan. It is meant to leave your source files unedited until you approve the plan (tell it to go ahead).

Three ways in:

  • Shift+Tab during a session, until the status bar shows ⏸ plan mode on.
  • /plan followed by your request, for example /plan add a strandedness column to the samplesheet parser.
  • claude --permission-mode plan when you start it.

When the plan is ready, the agent presents it and asks how to proceed. The options, with their exact labels:

  • Yes, and use auto mode: auto mode decides what runs without a prompt. If auto mode is unavailable, this reads Yes, auto-accept edits. If your session started with bypass, it reads Yes, and switch to BYPASS PERMISSIONS (no further prompts) for this session. Bypass skips most prompts.
  • Yes, manually approve edits: each edit still asks you.
  • No, keep planning: you say what to change.

The setting showClearContextOnPlanAccept adds a first option that approves and also clears the planning context. Look at your approval prompt to see whether it is on.

Note

At the approval prompt, Shift+Tab approves the plan. If you want to think, change something or back out, press Esc first. To leave plan mode when no prompt is open, press Shift+Tab.

Two more details:

  • Where the plan lives: plans are written to ~/.claude/plans/ by default (the plansDirectory setting changes the folder). Ctrl+G opens the proposed plan in your default text editor so you can edit it before the agent proceeds. Approving exits plan mode and switches to the mode you chose; to plan again, use Shift+Tab or /plan.
  • Side helper: in plan mode the agent can hand research to the built-in Plan subagent. It is read-only, so the main conversation stays read-only too.

OpenCode has a built-in plan agent. It explores and plans without editing normal project files, and it can edit only under its plan directory, ~/.opencode/plan. That edit restriction is a deny rule, and saved approvals do not override a deny. Its shell commands follow the normal permission rules.

The base policy for every agent allows everything except asking before reading .env files, so shell commands can run without a prompt. Check the permission rules in your version before you rely on the plan agent.

You can turn the plan agent off with {"agents": {"plan": {"disabled": true}}}.

To find out how to switch to the plan agent and whether it has an approval step, read the OpenCode agents page for your version.

Review the plan like a reviewer

A plan is text from a model that has not yet run anything. Read it the way you would read a methods section from a collaborator you have not worked with before. A checklist:

  1. What files will it touch? Anything outside the task is a question to ask.
  2. What does it assume about the data? “IDs are unique” or “the file has a header” are guesses until checked against the real files.
  3. What could it break? Callers, config, tests, outputs other people read.
  4. How will it verify, and is the check independent of the code it writes? A test the agent writes for its own code can share its mistake. Compute one value some other way, for example with awk or wc.
  5. Are the steps small enough to review one at a time? A step names one change, so “Update everything” needs splitting.
  6. What is not in the plan? Missing edge cases, missing tests, no mention of a rollback.

If an answer is bad, choose No, keep planning and say what to change, or edit the plan yourself with Ctrl+G.

What a plan does not guarantee

  • A plan is advice. An approved plan is only as good as your review of it.
  • The agent can deviate. The agent can still change course after approval. Afterwards, read the diff against the plan: every changed file should be one the plan named. /code-review reviews the diff in a fresh subagent that never saw your conversation.
  • Plan mode may be an instruction only. In an interactive terminal session where bypass permissions is available, Claude is only instructed to plan without editing. Claude Code does not enforce it, and edits and shell commands run without a prompt (explicit ask rules and a few critical deletions still prompt). With -p, the Agent SDK and the VS Code chat panel, the blocks stay in place.
  • Deny rules always apply. A deny rule blocks in every mode, plan mode included.
  • Read-only has gaps. Plan mode holds back edits. Test how your MCP tools and shell commands behave in it before you trust it near anything important.
  • The plan sits outside your repository by default. The plan file lives in ~/.claude/plans/. Keep your own project under Git.

When to plan, and when not to

  • One-line fix with an obvious check: just ask for it.
  • Unfamiliar code, changes across several files, and anything that touches paths where your data lives: plan first.
  • Open-ended exploring: a vague prompt is fine, at the cost of more correction.

Keep the approved plan

The plan in ~/.claude/plans/ is easy to lose track of. Ask the agent to save the approved plan into your project, for example as PLAN.md, then commit it.

A related pattern: ask the agent to interview you until it could write the spec, save it as SPEC.md, then start a fresh session (an empty conversation) to build from it. The fresh session has a clean context and a written definition of done.

Exercise: review a bad plan

Everything here is a mock on your laptop, and no model runs. Save mock-plan.md and samplesheet.csv. The plan says it will make a samplesheet parser accept a new strandedness column. Read the CSV, then go through the six checklist questions and write down every problem you find. Aim for at least four.

Answer key
  • No verification step. Step 6 reports success, and no step runs the parser or compares against an independent count.
  • A file outside the parser. Step 4 edits conf/base.config and renames a parameter, which can break every command line and config that uses the old name. The task covered only the parser.
  • An unchecked assumption about the data. Step 3 says sample IDs are unique. In the CSV, S03 appears twice (lanes L1 and L2), so a dictionary keyed by sample_id silently keeps only one row.
  • One step is too big. Step 5 covers modules, docs and tests at once. Ask for it to be split and reviewed piece by piece.
  • Also worth noting: S04 has an empty fastq_2, and the plan leaves that open (what is not in the plan). Step 2’s default of unstranded may quietly hide a missing column in a real run.
Review the plan the agent proposes for your next real task with the checklist before approving. Write down one thing you changed or rejected.
Ask for the plan to be saved to a file in your project, and open the file to check it matches what you approved.
