Bundle a Plugin

At the forest’s edge a satchel waits to be packed with the smith’s finest skills and their tests. Whatever you carry, others will unpack, and whatever you unpack from another traveller’s satchel runs with your own authority. A pack that looked fine on the table once split open on a stranger’s back. Pack with care, and open with more.

  • Goal: you will package Skills (and their evals) as a plugin, validate it, and see why installing one is a trust decision.
  • Before you start: Test the Skill. This is an optional side quest. An MCP server is an add-on connection that gives the agent extra tools.
  • Time: about 20 minutes.

A single Skill in your folder helps you. You need a plugin when a group should install the same set and get updates. A plugin is a folder that bundles Skills and, optionally, agents (helper assistants with their own instructions), hooks (scripts the harness runs at set points) and MCP servers.

The smallest plugin is a manifest (the file that describes the plugin: its name, version and author) and one Skill. Only name is required in plugin.json:

{
  "name": "fasta-tools",
  "description": "Small checks for FASTA files, as a teaching example.",
  "version": "0.1.0",
  "author": { "name": "Agent Odyssey contributors" }
}

Layout rules that trip people up:

  • Only plugin.json goes inside .claude-plugin/. Skills, agents and hooks go at the plugin root (skills/<name>/SKILL.md, agents/, hooks/hooks.json). Components placed inside .claude-plugin/ do not load.
  • The plugin name becomes a namespace (a prefix that keeps names from clashing), so the Skill is invoked as /fasta-tools:check-fasta.
  • Put your evals in evals/<case>/ so they travel with the plugin.

Try it without installing anything. If you do not have ./fasta-tools, clone or download the course repository and copy exercises/forge/fasta-tools into your folder, or use your own plugin folder:

claude --plugin-dir ./fasta-tools      # load for this session only
claude plugin validate ./fasta-tools   # checks files are well formed
claude plugin validate ./fasta-tools --strict   # also fails on warnings

After editing, run /reload-plugins in the session. On the example exercises/forge/fasta-tools (Claude Code 2.1.325), validate exited 0, with only an icon warning that matters for marketplace submission. Validation checks syntax and schema, and evals check behaviour.

To share, a marketplace is a repository with .claude-plugin/marketplace.json listing plugins and where to fetch them. People add it once and install by name.

OpenCode has its own plugins: code (.ts or .js) that adds tools and hooks, loaded from .opencode/plugins/ or ~/.config/opencode/plugins/, or listed in its config as npm packages, git repositories or local directories. Check the current OpenCode docs for the exact config key, and for whether OpenCode reads a Claude plugin.json.

A plain SKILL.md under .claude/skills/ is found by OpenCode too. If your group uses both tools, shipping the Skill that way is the portable route.

Installing one is a trust decision

A plugin you install can run arbitrary code on your machine with your user privileges. Hooks, monitors (background watchers that feed output to the agent), and local MCP and language servers (programs that give editor-style code checks) run outside the sandbox and the permission rules. A plugin’s bin/ folder holds executables that go on Claude’s shell PATH (the list of places commands are found), so Claude can run them, and each call follows your permission rules. Skills and agents enter the context as instructions, and instructions can steer the agent too.

Before installing or updating a plugin:

  1. Check where it comes from. A marketplace name says who publishes it. Reading the plugin shows what it does.
  2. Read hooks/hooks.json, .mcp.json, and anything in bin/. These are where code lives.
  3. In a session, /plugin shows what will be installed. claude --plugin-dir <dir> plugin details <name> prints a list of the plugin’s components without starting a session.
  4. Remember that auto-update can change files you reviewed, so re-read a plugin after each update. Pin a version for plugins you publish.

When a team shares Skills

  • Keep project names and conventions in one file. Put the reference genome build, the sample-ID pattern and the results folder names in a project-facts file (a plain file that lists them) that every Skill reads. Another lab can then reuse your Skills with its own file.
  • Keep discovered details apart from team standards. A pattern the agent finds in your code is an observation. A person confirms it before it becomes a standard.
  • Check generated copies. If you generate copies of a SKILL.md, run a check in CI (automated checks that run on every change) that fails when a copy differs from its source.
  • Merge blocking is a repository setting. Whether a bad change is stopped depends on repository rules and required checks. A review step written in a Skill is advice unless a required check backs it.
Turn the Skill you wrote into a plugin folder with a plugin.json, then run claude plugin validate on it and read the output.
