Write Permission Rules

Deeper in the Crypt a chalk circle is not enough, and an Astral does not stop at a door it was never told about. Warden Hesper shows you how to write wards: rules about what it may touch and what it must ask about. She says a ward is only as good as its edges, and she has watched an Astral stroll through a gap a hand’s width wide. Learn where your wards end.

  • Goal: you will write permission rules that hold, and know where they stop holding.
  • Before you start: Test Permissions and the Sandbox.
  • Time: about 20 minutes.

The harness (the program around the model) enforces permission rules. A line in your instructions file (such as CLAUDE.md, a text file the agent reads at the start) asking the agent to avoid something is guidance; only a rule the harness enforces changes what is allowed.

A single deny rule in a file is enough to block one action. A real project needs a set of rules, so sort every action into three bins:

  • allow: safe and routine.
  • ask: you want to decide each time.
  • deny: never.
  • Claude Code
  • OpenCode

Rules live in a settings file, as Tool(specifier):

{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(pytest *)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(./.env.*)"]
  }
}
File Who it affects
~/.claude/settings.json all your projects
.claude/settings.json everyone on the project, if you commit it
.claude/settings.local.json only you, in this project

A deny from any file beats an allow from any file. A space before the * matters: Bash(ls *) matches ls -la but not lsof. Restrict reads with Read(...) deny rules; a .claudeignore file does not restrict access.

OpenCode’s default policy allows everything except reading .env files, which it asks about, and a command in its shell can touch any file you can. Rules are an ordered array and the last match wins:

{
  "permissions": [
    { "action": "*", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" }
  ]
}

Start with the ask-everything rule, then narrow, then put denies last.

Where rules stop holding

  • Rules that match command arguments are fragile: Bash(rm *) does not match /bin/rm or bash -c 'rm ...'.
  • Claude Code’s sandbox (an operating-system boundary around shell commands) is off by default. When on, it limits shell commands only: Claude’s file tools and MCP servers (programs that add tools from outside) run outside it, and by default it can still read ~/.ssh.
  • Secrets stored in environment variables (named values the shell passes to every program it starts) are inherited by every command the agent runs.

Treat rules as one layer. Git commits and a throwaway folder are other layers.
