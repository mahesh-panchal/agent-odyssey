Test the Leash

The Beast has fallen in beside you, strong and willing, and it wants to run ahead. At the Crypt door the warden hands you a short leash and a feather. “Do not trust a rope you have not pulled,” she says, and she has heard the kennel master swear that this lead holds anything. You ask the Beast for one small poem and watch what it does at the end of its lead. Then she shows you a wall of stone around its paws: test the leash, then test the wall.

  • Goal: you will watch an agent ask before it acts, switch it between modes, block one file with a rule, and see an operating-system boundary refuse a command.
  • Before you start: Know Your Gear, and Recruit the Beast, which installs an agent (Claude Code, or OpenCode with Ollama) and starts it in a throwaway folder. Each step has a tab for each route. The OpenCode route also needs Docker for step 4. The Prerequisites page lists the tools for the optional steps.
  • Time: about 30 minutes. Everything happens in a scratch folder with invented content.

Do this before an agent touches real files. An agent (a model with tools, running in a loop) can write files and run commands. Two separate guards limit it:

  • Permissions. The program around the model (the harness) asks you or refuses before one of its tools runs. A tool is an action such as writing a file or running a command.
  • Sandbox. The operating system limits what a shell command can touch, whatever the model asks for.

You test each guard in a safe folder, one at a time. Every command below runs in ~/odyssey-scratch/leash. If you open a new terminal, run cd ~/odyssey-scratch/leash and check with pwd before you continue. The first test is the simplest possible job: a poem in a text file.

mkdir -p ~/odyssey-scratch/leash && cd ~/odyssey-scratch/leash

1. Permissions: the agent asks first

  • Claude Code
  • OpenCode + Ollama

Start Claude Code in its default mode and give it a small job:

claude
Write a four-line poem about a thermocycler to a file called poem.txt.

Claude shows a prompt before it creates the file. Read it: it names the tool, the file path and the contents. The choices include yes once, yes for the rest of the session, and no. Choose yes once, then check the result in a second terminal or after you exit the session with /exit:

cat poem.txt

Run a prompt for a different file name and answer no. Claude reports the refusal and no file appears. It may offer another way to do the job; decline that too.

OpenCode’s default policy allows edits without asking, so first add a rule that makes it ask. In ~/odyssey-scratch/leash, create a project config file named opencode.json:

{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "edit", "resource": "*", "effect": "ask" }
  ]
}

Each rule has an action (what the agent wants to do), a resource (what it is done to; * matches anything) and an effect (allow, ask or deny). Send a small job from the shell:

opencode run -m ollama/qwen3:4b "Write a four-line poem about a thermocycler to a file called poem.txt."

opencode run cannot ask you anything, so it rejects the request. The output says This non-interactive run cannot ask the user for permission, so the request was rejected, and no poem.txt appears.

For the interactive question, start opencode in the folder, type /models to pick your Ollama model, and send the same prompt. The prompt offers Allow once, Allow always and Reject. Choose Allow once, then check the result in a second terminal or after you exit:

cat poem.txt

Run a prompt for a different file name and choose Reject. Nothing is written.

2. Modes: how much it asks

  • Claude Code
  • OpenCode + Ollama

A permission mode sets what the harness asks about. Shift+Tab cycles the common modes inside a session, and the status bar shows the current one.

Mode Behaviour
default asks before edits, shell commands and network requests
acceptEdits auto-accepts file edits and common file commands (mkdir, touch, mv, cp)
plan reads and proposes; no edits until you approve a plan
bypassPermissions skips most prompts; for isolated containers and virtual machines only

Try plan mode. Exit with /exit, then:

claude --permission-mode plan
Write a four-line poem about a gel box to a file called poem2.txt.

Claude proposes a plan and waits. Reject the plan, exit with /exit, then run ls: poem2.txt does not exist. Plan mode answers “what would you do?” without doing it.

OpenCode has agents (preset bundles of instructions and permissions) in place of a mode table. The build agent is the default. The plan agent explores and plans and does not edit your project files. In the interface, Shift+Tab cycles between agents.

Try the plan agent from the shell:

opencode run --agent plan -m ollama/qwen3:4b "Write a four-line poem about a gel box to a file called poem2.txt."

The plan agent declines to write the file. Run ls: poem2.txt does not exist. The plan agent stops file edits only. Its shell commands still follow the rules in your config, and the default policy allows them.

3. A rule that always applies

  • Claude Code
  • OpenCode + Ollama

A permission rule is a line in a settings file that allows, asks about or denies one action. Rules are checked deny first, then ask, then allow, and the first match decides. Create an invented secret (a .env file is where programs often keep passwords and keys) and a rule that blocks reading it. Exit the previous session first with /exit:

cd ~/odyssey-scratch/leash
echo "FAKE_API_KEY=not-a-real-key" > .env
mkdir -p .claude
cat > .claude/settings.local.json <<'JSON'
{
  "permissions": {
    "deny": ["Read(./.env)"]
  }
}
JSON
claude

Type this into Claude, not into the shell:

Show me what is in .env.

Claude cannot read the file with its file tools. Claude Code also applies the rule to shell commands it recognises as file readers, such as cat .env. It cannot apply the rule to a program that opens the file itself, such as python3 -c "print(open('.env').read())". The sandbox in the next section limits what such a program can write and send over the network. By default it can still read .env, so keep real secrets out of the folder.

A permission rule is one entry in the permissions list of a config file. OpenCode checks the rules in order, and the last matching rule wins. Create an invented secret (a .env file is where programs often keep passwords and keys) and a rule that blocks reading it:

cd ~/odyssey-scratch/leash
echo "FAKE_API_KEY=not-a-real-key" > .env
cat > opencode.json <<'JSON'
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "edit", "resource": "*", "effect": "ask" },
    { "action": "read", "resource": "*.env", "effect": "deny" }
  ]
}
JSON

Ask for the file twice, once for the read tool and once for a shell command:

opencode run -m ollama/qwen3:4b "Use your read tool to show me what is in the file .env."
opencode run -m ollama/qwen3:4b "Run the shell command: cat .env  and show me the exact output."

The first run fails with Permission denied: read. The second prints FAKE_API_KEY=not-a-real-key. The rule covers the read action only, and cat is a shell command. Add a rule for the shell and run the second command again. Replace the file with all three rules, so the first one stays:

{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "edit", "resource": "*", "effect": "ask" },
    { "action": "read", "resource": "*.env", "effect": "deny" },
    { "action": "shell", "resource": "cat *", "effect": "deny" }
  ]
}

Now it fails with Permission denied: shell. A rule blocks the commands it names. A program that opens the file itself, such as python3 -c "print(open('.env').read())", still reads it, so keep real secrets out of the folder.

4. The sandbox: the operating system says no

  • Claude Code
  • OpenCode + Ollama

The sandbox is a boundary the operating system enforces around the shell commands Claude runs, and around the programs those commands start. By default it allows writes in the project folder and a temporary folder, and it routes network traffic through a proxy (a gatekeeper program that traffic passes through) that starts with no allowed domains. It can still read most of your machine, so keep secrets out of reach with the rules above. It does not cover Claude’s own Read, Edit and Write tools or MCP servers (programs that offer Claude extra tools); those stay under permission rules.

Set-up differs by system:

  • macOS: nothing to install.
  • Linux and WSL 2 (Windows Subsystem for Linux): install the two helper tools the sandbox is built from, sudo apt-get install bubblewrap socat (Debian, Ubuntu) or sudo dnf install bubblewrap socat (Fedora), then restart Claude Code.
  • Native Windows: commands run without a sandbox. Use WSL 2.

Start Claude, type /sandbox, and choose a mode:

  • Auto-allow: sandboxed commands run without asking.
  • Regular permissions: every command still asks.

Both modes enforce the same boundary. Choose regular permissions for this exercise so you see each command first. Then ask:

Run this command and show me the exact result: touch ~/sandbox-probe
Run this command and show me the exact result: curl --noproxy '*' https://example.com

Expected results:

  • touch: Operation not permitted on macOS, Read-only file system on Linux and WSL 2.
  • curl: Could not resolve host.

Both commands failed because the operating system refused, and no instruction to the model can override that. If Claude offers to run a blocked command outside the sandbox, answer no. If the touch succeeded, the sandbox is off. Run rm ~/sandbox-probe, switch /sandbox on, and do not continue until the touch fails. Run the probes through Claude and not with the ! prefix, which runs a shell command directly, outside the sandbox.

To open one path or domain for a task, add it under sandbox in settings.json (.claude/settings.json inside a project, or ~/.claude/settings.json for every project):

{
  "sandbox": {
    "enabled": true,
    "filesystem": { "allowWrite": ["~/odyssey-scratch/build"] },
    "network": { "allowedDomains": ["github.com"] }
  }
}

OpenCode’s documentation describes permission rules but no operating-system sandbox. Its shell commands run with your user’s authority: your files, your processes and your network. OpenCode enforces its own rules inside its program, and nothing at the operating-system level limits what a command it runs can touch. A boundary has to come from outside the agent, and a container is the simplest one to test.

A container is an isolated Linux environment with its own filesystem; it sees your files only where you mount them in. Docker is a common tool for this. Install Docker Desktop (or Docker Engine on Linux) and start it before you run this command. The first run downloads the python:3.11 image, which is large. The command mounts the scratch folder and cuts the network:

docker run -it --rm --network none -v ~/odyssey-scratch/leash:/project -w /project python:3.11 bash

Inside, run ls / (a different filesystem from yours), curl https://example.com (fails, no network) and touch /project/inside.txt. The file appears in your scratch folder because it is the mounted project folder, the only part of your machine the container can change. Type exit to leave. This tests the boundary itself. Running an agent inside one takes more set-up than this lesson covers.

5. Optional: a container

On the Claude Code route you do not need a container for this lesson, because /sandbox already gives you a boundary to test. On the OpenCode route, step 4 used one.

For an agent inside a container, Anthropic’s reference setup is a dev container (a container definition your editor starts for you). Anthropic’s docs allow the flag --dangerously-skip-permissions (the same as bypassPermissions mode) only there, because the container is the boundary. Two limits remain: the agent can still change the mounted project folder, and a malicious project can reach anything inside the container, including Claude’s login in ~/.claude. Mount no host secrets such as ~/.ssh, and restrict the network.

Clean up

Exit the agent. On the Claude Code route, switch /sandbox off if you do not want it on. Then delete the probe file and the scratch folder, nothing else:

cd ~ && rm -f ~/sandbox-probe && rm -rf ~/odyssey-scratch/leash
