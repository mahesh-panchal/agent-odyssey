The Locked Cabinet

  • Goal: you will keep keys, settings and sensitive data out of the agent’s reach, and know what changes on a shared cluster.
  • Before you start: Grow the Carapace. A deny rule is a setting that blocks the agent’s file-reading tool from a path.
  • Time: about 15 minutes.

Much research data is not sensitive. Some of it is, and then special agreements apply. Your own data agreement and your cluster’s policy come first. This quest uses no real data and practises habits, so that the careful choice becomes automatic.

Three ideas

  1. A prompt may leave your machine. With a hosted model, anything the agent reads may be sent to the provider. A model running locally (on your own machine, for example through Ollama) keeps prompts on your machine, though web or tool calls it makes may not. Your agreement decides whether either is allowed for your data.
  2. Secrets stay out of content. API keys, tokens, SSH keys and passwords belong in a secret store, kept out of the project folder, and out of chats and any instructions file you commit. An environment variable is visible to any command the agent runs, so a read rule alone does not seal it.
  3. A shared cluster is shared. What is fine on your laptop can disturb other people on a login node, or break a data policy on shared storage. Cluster rules apply to agents exactly as they apply to you.
Note

A deny rule on your secrets files stops the agent’s file-reading tool. It does not apply to a Python or Node script that opens the file itself. So also keep secrets out of the project folder, and use a sandbox or shell rules where you can. For another tool, check its documentation on shell reads of denied files.

Personal data and where an agent may send it

  • Reading a file discloses it. With an externally hosted model, everything the agent reads goes to the provider. If the agent opens a project .env file, treat its keys as exposed and rotate them. Keep secrets outside folders the agent can read.
  • Personal data needs more than a no-training promise. Sending personal data to a provider can count as processing under GDPR (the EU data protection law). Ask your data steward which accounts are approved, and use an institutional account for work. Ask them too whether you need a lawful basis (a legal reason to process), a processor contract (a written agreement with the provider) and a transfer basis (a legal route for sending data abroad).
  • Limit where the agent can send data. Instructions alone do not stop a send. A sandbox or network limit can.

What stays behind: transcripts

The agent keeps a record of the session so that it can resume. Anything that passes through a tool goes into that record: file contents, command output, pasted text. If a tool reads a .env file or a command prints a credential, the value is written to the session transcript. Transcripts are stored locally in plaintext, for 30 days by default.

In November 2026 a coding-tool vendor reported an incident: an access key issued to one of its vendors was exposed, and a storage bucket held limited coding agent traces. A small number of those traces contained credentials that had not been redacted.

Habits that cost little:

  1. Reference a secret, do not type it. Write psql "$DATABASE_URL", so the command, and any rule saved from it, holds a variable’s name.
  2. Approve patterns, not literal commands (npm run *). When you choose “Yes, and don’t ask again”, Claude Code saves an allow rule in .claude/settings.local.json. On first write in a git repository it adds that file to your global git excludes. If you create the file by hand, add it to .gitignore yourself. Open the file now and then, and delete any saved rule that contains a secret.
  3. Rotate anything that has been in a transcript. Deleting the file does not reach backups, copies or a vendor’s storage.
  4. Keep less. The cleanupPeriodDays setting shortens how long transcripts stay. claude purge deletes a project’s state (try --dry-run first). CLAUDE_CODE_SKIP_PROMPT_HISTORY=1 skips writing transcripts and prompt history.
  5. Make a leak worth little. A token for one repository that expires in an hour is a small loss if it leaks. A GitHub installation access token expires after 1 hour. Where a service only issues long-lived keys, give the agent a separate, narrow key that you can rotate without breaking your own work.

Redaction helps and has limits. A scanner matches formats, and a password after -p has none.

Unpublished ideas and results

A common worry: my unpublished results or ideas will leak and someone will get there first. The habits below lower the chance and the cost of being wrong.

Training use means a provider may learn from your prompts to improve future models. For Claude Code:

  • For Free, Pro, Max and Ultra accounts, training use depends on a privacy setting that you can change.
  • For Team, Enterprise and API accounts, code and prompts sent to Claude Code are not used for training under commercial terms, unless the customer opts in.
  • Retention for consumer accounts is 5 years if you allow model improvement and 30 days if you do not. Commercial accounts have 30 days as standard, and zero data retention for qualified Enterprise accounts.
  • Read the terms of the exact tool and plan you use, including the privacy page of any chat app. Other providers’ terms differ by product and plan; read the terms for the exact plan you use.

Habits:

  1. Keep unpublished ideas, results and sequences out of consumer chat tools unless the terms say how your text is used and you accept that.
  2. Prefer an agreement your institution has reviewed. Ask your data steward or research office what is approved. They can advise on contracts and ownership.
  3. Consider a local model. Ollama does not see your prompts or data when you run locally. Tools and web calls the model makes may still send data out. A free hosted tier still sends your prompts to a provider.
  4. Date-stamp your work. A preprint, a repository tag or a dated lab notebook entry records when you had it.
  5. Share on a need-to-know basis. Send collaborators what they need for the task.

Bonus

Nothing here is checked, and nothing depends on it. The real rules are in a document your group holds.

Find the data-handling agreement or policy that applies to your project (or ask your group leader where it is). Read the passages about where data may be processed and whether it may be sent to external services, and write down in your own notes what they say.
List where your own API keys and settings files live (for example a .env file or a shell profile), and check that your agent’s permission rules deny reading them.
