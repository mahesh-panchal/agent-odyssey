Carry Context Between Sessions

You wake at the mill with a fresh Astral and a half-finished job. It knows nothing of yesterday except what loads by itself or lies written down, and yesterday you wrote nothing. Scribe Linnea keeps a ledger of notes at the mill for exactly this gap, and she knows when to tip the hopper out and begin again. Learn what belongs in the ledger, and the next visit starts where the last one stopped.

  • Goal: you will decide when to start a fresh session, and write a short handoff note and memory entry that a fresh session can act on, with what was checked kept apart from what was not.
  • Before you start: The Context Window. Commands here are Claude Code commands.
  • Time: about 25 minutes.

You stop work on Friday with a half-finished refactor. On Monday you open a new session (one conversation with the agent, which has its own context: the text it can see right now). Each session begins with a fresh context window and no conversation history from before, so the new session does not know your goal, what you tried or what you checked.

You will meet this gap in every long task. If you write down what matters, a fresh session continues the work and you stop re-explaining the same background. If you do not, you pay for it in time and in wrong guesses.

What a new session already has

Only some things reach a fresh session without you typing them.

  1. The instructions file (CLAUDE.md in Claude Code). A file you write, loaded at the start of every session. Good for stable facts and conventions: how to run the tests, which folders are off limits.
  2. Auto memory. Notes the harness (the agent program around the model, such as Claude Code) writes itself, from your corrections and preferences. In Claude Code, /memory lists and opens them.
  3. Files in the repository (the project folder under version control): code, tests, a README and, if you keep one, a progress or handoff file.
  4. Git history. A commit is a saved snapshot of the project with a message you or the agent write. The list of commits shows what changed and when, and it lasts.
  5. Your handoff note. A short file about the state of one task, written for the next session.
What Goes where Lifetime Who writes it Trust
Stable rules and conventions Instructions file Until you edit it You High if short and checked
Preferences the harness picked up Auto memory Until deleted The harness Medium: it can be wrong
What the files say now Files in the repository Until edited or deleted You or the agent Medium: files can be stale
State of one task Handoff note Until the task is done You, or the agent drafts and you review Only as good as your review
What changed, and why Commit messages in git history Durable You or the agent Reliable for what changed; the why is only as good as the message

Anything only said in chat is gone. That covers the decisions, what failed and why, and which sample misbehaved.

Start fresh or carry on

Starting fresh opens a new, empty conversation. Your files stay as they are. Neither choice is free: clearing too early makes the agent re-read files and rediscover decisions, and carrying on too long keeps a crowded or degraded context.

Start fresh when:

  1. The task is new and unrelated. Run /clear between unrelated tasks. It starts a clean conversation, and only what you wrote down travels with you, so write down anything you need first. A name, as in /clear oauth-migration, labels the conversation you leave so you can reopen it with /resume later.
  2. The agent repeats a wrong claim after two corrections. Clear, and write one better prompt that includes what you learned. A third correction adds to a conversation that already holds two failed attempts.
  3. The agent forgets early instructions or contradicts itself. Start fresh, and move the instruction into the instructions file.
  4. A task is finished and a verified result is committed. The result lives in your files and in git, so the conversation has done its job.
  5. You have been away and the next task is new. A fresh session has no history to re-send.

Carry on when:

  • It is the same task and early decisions still matter. The next step needs the same files, the decisions you made and what was already tried.
  • The agent is on track. Nothing is repeated or contradicted, and clearing a working session throws away good context.
  • You are returning to a named session. /resume (or claude --resume <name>) reopens a session you chose, and claude --continue reopens the most recent one in this directory. Resuming with claude --resume or claude --continue restores the messages, the model and the permission mode (what the agent may do without asking).

/compact replaces a long history with a summary and stays in the same conversation. It is a middle path for a crowded window on a task you still need.

Situation Action
New task, unrelated to this conversation /clear
Same task, agent on track, plenty of room Carry on
Same task, crowded, early decisions matter /compact, naming what to keep
Wrong claim repeated after two corrections /clear, then one new prompt
Back after a break, still need the conversation /resume or claude --continue
Back after a break, next task is new Fresh session
Task done, verified result committed Write down what matters, then /clear

Before you clear

Write down what only exists in the chat, and commit the result so the state is recoverable. Your files and memory remain, and the instructions file and auto memory load again in the new session. If you clear by mistake, /resume can reopen the old conversation.

Write the note before you run /clear. You can write it yourself or ask the agent to draft it (the last section of this page covers drafts). If the note belongs to a repository, commit it with the result, so git holds a matching record.

What a good handoff note contains

Keep it short, so reading it costs less than rediscovering the state. Point to files and commands, and let the next session run them for fresh output.

  • Goal in one line.
  • Current state: branch, last commit, what runs and what does not.
  • Decisions and the reasons, including options you rejected.
  • Verified, and how; not verified. Two separate lists. For each verified item, the command and what it showed.
  • What failed and should not be retried.
  • Next steps, in order.
  • Pointers: file paths, commands, job IDs, work directories.
  • Open questions that the next session should settle.

This is a mock handoff note for a mock task. The file names and numbers are invented.

# HANDOFF: qc_filter.py refactor (mock example)

## Goal
Replace the per-read loop in qc_filter.py with a vectorised version, same output.

## State (git branch refactor-qc, last commit a1b2c3d "qc: add vectorised mean quality")
- New function mean_qual_fast() is written and called from main().
- Old function mean_qual() is kept for comparison. Do not delete yet.

## Decisions
- Keep both functions until all samples are compared (a bug here would silently change which reads pass).
- Threshold stays at mean Q20, as in the lab protocol.

## Verified
- tests/test_filter.py: ran `pytest -q`, 6 passed.
- sample_A: `diff <(python qc_filter.py A.fq) old_out/A.txt` gave no output.

## Not verified
- Samples B and C have not been compared with the old output.
- Reads shorter than 30 bases: no test covers them.
- Speed gain: not measured.

## Failed, do not retry
- Using numpy on the raw quality string: wrong values for the Phred offset. Convert to integers first.

## Next steps
1. Compare B and C against old_out/ with the same diff command.
2. Add a test for a 10-base read.
3. Only then delete mean_qual().

## Open questions
- Should the threshold be a command-line option?

Where to put it, and how to start the next session

Put the note in a file the next session can find. Two options:

  • A file in the repo, such as HANDOFF.md, if the team should see it.
  • A personal file that git ignores, such as HANDOFF.local.md, with its name added to .gitignore (the file that lists what git leaves out). This is the simpler choice. You point the next session at it by name.

Anything in CLAUDE.md loads every session and takes room in the window, so keep a handoff note out of it and let the next session read the note only when you ask.

Then start the new session with a prompt like this:

Read HANDOFF.md, then tell me your understanding before changing anything.

The agent restates the goal and state in its own words, and you compare that with what you know. This is a cheap comprehension check that can catch a misreading of the note. The restatement comes from the same model that read it, so the note’s claims still need checking against the source.

You can ask the agent to draft the note at the end of a session. Review it yourself, since a draft can overstate what was verified (“all tests pass” when none were run in that session).

Two more habits help a long task: make git commits with descriptive messages so bad changes can be reverted, and begin each session by reading the progress file and the recent git log, then run the project’s tests as a quick check before new work.

When a wrong claim gets in

Memory the harness wrote can be wrong, and a wrong line is loaded again every session. This is context poisoning: a wrong statement, perhaps planted in a web page the agent read, enters the context and later answers build on it.

Where the wrong claim sits What clears it
The conversation /clear, then one new prompt that folds in what you learned. /rewind (a command that rolls the conversation back to an earlier turn) can return to before the bad turn.
Auto memory or the instructions file Open /memory, read what has been written about your project, and delete the line. A fresh session loads it again until you do.
A handoff note Edit the line, then say in the note what was actually checked.

Check a claim against its source, such as the data, the program’s own --help or the paper, before it goes into the instructions file, auto memory or a note.

Commands:

  • /memory: lists memory files, toggles auto memory, opens the folder. Auto memory is per git repository and machine-local.
  • /clear: new empty conversation; the old one stays resumable. /new is an alias.
  • /compact [focus]: replace the history with a summary.
  • /resume and claude --resume [name]: reopen an earlier session.
  • claude --continue: the most recent session in this directory.
  • /rename: name the current session.
  • /rewind: return the conversation to an earlier turn.
  • /export: writes the conversation as plain text for a person to read. Transcripts are long, so write a short curated note yourself.

Commands: /new starts a new session and /sessions lists earlier ones. Check OpenCode’s documentation for compacting and export. The handoff note itself is just a file, so the practice carries over. Check OpenCode’s documentation for how it loads project instructions and memory. A local model with a small window means starting fresh sooner, so keep the note short.
