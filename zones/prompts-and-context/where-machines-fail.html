Where Machines Fail

A boaster at Gaia’s Rest swore his Astral could fly. You led it to the mill roof, and it spread its wings, glided a few fine yards and landed in the mud. Over the mill door Miller Garrick has hung a sign with two lists: what the machines do well, and what they only seem to do well. Counting letters is on the second. Read both lists, then learn which jobs to hand a creature and which to give to an Automaton.

  • Goal: you will sort jobs into “ask the model” and “run a script”, and name the other ways a model fails with one mitigation each.
  • Before you start: Tokens, Not Letters, and a terminal.
  • Time: about 15 minutes.

A language model is good at some jobs and bad at others, and a wrong answer often looks like a right one. Knowing which jobs are which, before you trust the output, saves time and prevents errors. Using a model is your choice; this lesson shows where the risk sits if you do.

Where a model helps: the result is checkable

Use a model where you can read the result, or run it, and judge it yourself:

  • summarising text
  • drafting prose, such as a README or a methods first draft
  • explaining code or an error message
  • converting formats, for example a samplesheet CSV to JSON (a structured text format)
  • first drafts of code that you will then test

Summaries can leave things out or bend them. Spot-check against the source: numbers, gene and sample names, direction of effect, negations. Omissions are harder to see, so skim the abstract and limitations yourself. Ask the model to quote the supporting lines first, then summarise.

Where a model fails

Each failure below has the same shape: what goes wrong, then what to do about it.

Exact counting and arithmetic

Ask a model: “How many n are in banana?” The right answer is 2 (b-a-n-a-n-a). A model can get this wrong, and can be wrong while sounding sure.

Researchers disagree on why. One explanation is that the model reads tokens (chunks of letters), not letters. One study finds word length and the true count matter more than tokenisation. The fix works whichever cause is right.

The fix is to run a script:

echo banana | grep -o n | wc -l

It prints 2 (macOS pads the number with spaces). A model asked to write Python for a counting task does better than a model asked to answer it directly. So for exact counts, have the model write the script and read the script and its output.

The bioinformatics versions of the same trap:

You want Give it to
Number of sequences in a FASTA grep -c '>' file.fa, or seqkit stats
GC content, read length statistics a script, run by the agent, with the code visible
A p-value or any test statistic a stats library in a script you can read and re-run
Sum or mean of a column awk, or a script that prints the number

Ask for the command and its output, and treat a count stated in prose as a guess to check.

Hallucination

A confident statement that is false, such as a plausible DOI, gene ID or tool flag that does not exist. A model may recommend --min-quality for a tool that has no such option. Allow “I don’t know”, ask for word-for-word quotes first and restrict the model to supplied documents. Look up every ID in PubMed or Ensembl, or run the tool’s --help.

Sycophancy

The model tells you what you want to hear. It agrees with your wrong hypothesis, or softens a correct criticism when you push back. Ask “are you sure?” about a right answer and it may change to a wrong one. Ask for the strongest case against your idea, and hold back your preferred answer.

Long-context degradation

Accuracy and recall drop as the input (everything the model is given to read) grows, a decline sometimes called “context rot”, and relevant text in the middle is used less. Curate the input (head, counts, filtered tables) and start fresh for a new task.

Instruction drift

An early instruction is forgotten, for example after compaction (the program around the model replacing old conversation with a summary to free room). Keep a short instructions file (CLAUDE.md or similar, loaded at session start). Use a hook (a script that runs automatically at set moments, such as before a command) for must-never rules.

Non-determinism

The same prompt may give different answers, so run it twice and compare. Record the command, model and version, and treat the script the model wrote as the reproducible part.

Overconfidence

The model reports a task as done while it is unfinished, often because it had no way to check. Give it a check to run (tests, row counts, md5) and read the output.

Prompt injection

Text from fetched content that the model treats as an instruction, for example a README, PDF or FASTA header that contains instructions the agent follows. Treat fetched content as data, review commands before approving them, and remember no system is fully immune.

Restricted topics

Providers train models, and put filters around them, to refuse or limit help on topics they judge dangerous, such as biological weapons or malware. The filters can also catch legitimate work that looks similar. Two areas matter to bioinformaticians. In biology, a provider’s filters may send a request on a topic such as virology or toxicology to a less capable model, and the provider says false positives remain. In security, real-time safeguards may block or limit help with exploit or malware work, and providers offer an application route for verified professionals. The result can be a refusal or a thinner answer with no error message, so a poor answer on a legitimate topic may be a safeguard at work.

Check the reply for a notice that a safeguard blocked the request or that another model answered. Verify what you did receive with a database, a script or a colleague. Do not rephrase to dodge a filter, because bypassing a provider’s guardrails breaks its usage policy. Filters can also hit allowed work, and the provider’s policy says a block is no sign of a violation. Apply for the provider’s verified-access route for your field (Anthropic’s Cyber Verification Program is one example for security work), or use another tool for that step.

Stale knowledge

Newer tool versions or database releases postdate the model’s training. Check --version and the current docs, and look up the model’s training cutoff date in its documentation.

The decision rule

Ask yourself: can I check the result cheaply and independently? If yes, ask the model: a bad answer is likely to show (omissions may not, so check those deliberately). If the answer must be exactly right and cannot be checked, use a script.

Battle: ask the model or run a script

Bonus

Ask a model to count one letter in a long word (or a mock 40-letter DNA string), then check it with grep -o and wc -l. Note whether it was right, and how sure it sounded. One try is a demonstration and falls short of proof.
Have a model summarise a methods paragraph you wrote. Check every number, name and negation against your original, and note anything omitted.

Lore

Further reading. Optional.

  • Lost in the Middle: Liu et al., arXiv, paper. Why read: it shows recall is best for text at the start or end of a long input and weaker in the middle. A preprint.
  • On Faithfulness and Factuality in Abstractive Summarization: Maynez et al., ACL 2020, paper. Why read: it found hallucinated content in neural summaries; older models, but it shows why summaries need a spot check.
  • LLM The Genius Paradox: A Linguistic and Math Expert’s Struggle with Simple Word-based Counting Problems: arXiv, paper. Why read: its abstract says specialised math and coding models still struggle with simple counting and that reasoning before answering is the most reliable fix; its full text adds that explicitly asking coding models for Python code worked. A preprint, not peer-reviewed as far as we checked.
  • Improving Fable 5’s biology safeguards: Anthropic, article. Why read: it says biology requests can be re-routed to a less capable model, that false positives remain, and that dual-use topics such as virology still fall back.
  • Cyber Verification Program: Anthropic, docs. Why read: it explains when security work is blocked and how verified professionals apply for fewer interruptions.
  • Reduce hallucinations: Anthropic, docs. Why read: it gives habits such as allowing “I don’t know” and checking claims against quotes, the kind of fix for the confident-but-wrong rows in this quest; it says none removes errors.
