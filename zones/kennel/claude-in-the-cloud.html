Claude in the Cloud

A tower stands far above the Collegium, where the Claude Astral can work on a borrowed machine that vanishes when the job is done. It is a fine place to sketch and write, and the boasters make it sound fit for any task. Asked plainly, an academic lowers their voice: nothing precious should be carried to the tower. Learn what the tower is good for, and what you must leave at home.

  • Goal: you will say what a cloud session is, what leaves your machine when you start one, which jobs suit it, and how to review what comes back.
  • Before you start: Know Your Tools, Set Up Your Agent and Keep Secrets Out of Reach. You need git and a GitHub account only if you later start a session.
  • Time: about 15 minutes. The exercise is a worksheet on a mock file tree and needs no cloud account or model.

The rule for this page

You may be offered a way to run an agent on someone else’s computer. You need this lesson before you start one, because what you send is stored away from your machine. Decide what may go there first.

NoteCloud sessions are for drafting scripts and documentation. Data analysis stays on your machine or the cluster.

Use a cloud session for writing scripts, updating documentation and similar low-risk text work. Real data, controlled data, sample sheets with identifiers, genotypes and results stay out of a cloud session and its repository. Analysis runs on your own machine or the cluster, under your data agreement.

Think of the cloud agent as a drafting helper that returns a branch (a named line of commits in git) which you review and then run yourself, where the data lives.

Cloud sessions are optional. If you use one, the rest of the page shows how to keep sensitive material at home.

1. What a cloud session is

A cloud session is a Claude Code session that runs on Anthropic’s servers, away from your laptop. Each one gets a fresh virtual machine (a computer simulated inside a bigger one, thrown away afterwards) with a fresh clone (a full copy of a repository) of your code, made from its copy on GitHub. It keeps working after you close your laptop. When it is done, the work comes back as a branch, which you can turn into a pull request (a proposal on GitHub to merge that branch, with a place to review the changes).

Only committed files (changes you have saved into git history with git commit) travel, because the clone is made from GitHub. A committed CLAUDE.md (the instructions file Claude Code reads at the start of a session) and the project’s skills and agents come along. What stays behind:

  • your personal ~/.claude/CLAUDE.md (the same kind of file, kept in your home folder), skills, agents and user-level settings;
  • MCP servers (add-on connections that give the agent extra tools) you added only for yourself;
  • .claude/settings.local.json and interactive sign-ins.

2. What leaves your machine

Read this part twice. When you start a cloud session:

  • Your repository contents are cloned onto Anthropic’s VM. Anthropic reads only the repository you start the session in.
  • Your prompts and everything the agent reads and writes go to the model.
  • The session transcript (the saved record of the whole conversation, including tool output) is stored by Anthropic so you can return to it later.
  • Retention (how long Anthropic keeps stored data) depends on your account type: from 30 days up to 5 years. Check your plan’s current terms on the Data usage page in Lore. Deleting a cloud session permanently removes its event data.
  • Network level None may still let data exit. A network access level is the setting that says which internet hosts the VM may reach (None, Limited or Full; see section 5). The Anthropic API stays reachable even at None, which may allow data to exit the VM.
  • Environment variables (named settings handed to programs, often used for keys) set in a cloud environment can be read by any command Claude runs, and anyone who uses that environment can read the values.

Some organisation settings block cloud sessions outright, and your administrator can switch them off. Ask whether yours are available.

Keep controlled data out of the cloud repository. Treat the clone, the transcript and anything you paste as held by Anthropic. Read your data agreement before you push anything to a remote that a cloud session can see (a remote is the copy of a repository hosted elsewhere, such as on GitHub).

3. Good uses and bad uses

Fine for a cloud session (code and mock data only) Keep for your machine or the cluster
Write a samplesheet validator, tested on a three-row mock file Run the analysis
Write a QC summary plotting script, developed on mock data Load real counts, genotypes or results
Draft or update the README, changelog, docstrings Debug with real sample IDs in the repository
Refactor non-data code that has tests Anything under a data agreement
Review a pull request that holds no identifiers Anything that needs a local database or the cluster
Triage issues that hold no identifiers Anything that needs your institution’s network or files

A cloud machine has no GPU and no access to your institution’s network. Work that needs a GPU, a VPN (a private network link into your institution) or local databases stays on your side.

4. How to start

  • Claude Code
  • OpenCode + Ollama
  • Push first. claude --cloud "your task" starts a cloud session from your terminal. It clones the GitHub remote at your current branch, and your local folder is not used. Commit and push (save snapshots, then upload them to the remote) before you start, so the session sees your latest work. If the branch is not on GitHub the CLI prints Branch <name> is not on GitHub, and the session starts from a pushed commit or the default branch. One repository per session. You can also start from claude.ai/code in the browser.
  • Write a ticket-style prompt. That is a self-contained note like a work ticket: the problem, the expected result, and a command that proves it (in the example, pytest, a Python test runner). Be specific, name files and paste errors. Example, with no data in it:
Problem: scripts/validate_samplesheet.py accepts duplicate sample IDs.
Expected: exit status 1 and a message naming the duplicated ID.
Check: pytest tests/test_validate_samplesheet.py (mock rows only).
Add a test for the duplicate case. Only change files under scripts/ and tests/.

A repository with no real data anywhere in it is the safe one. Removing the data/ and results/ folders is not enough if real files sit elsewhere. A prompt line such as “do not read data/” is a request to the model and gives no protection. If the folder is in the repository, the cloud session can read it.

  • If there is no remote. When the repository has no git remote, or a GitHub repository does not have the Claude GitHub App (an app you install on a repository to let Claude clone it) installed, Claude Code bundles it and uploads the full history of all branches plus uncommitted changes to tracked files. Keep data out of this route entirely. Your history may already hold a file you deleted, and the bundle takes all of it. Check what is tracked and what your .gitignore covers first.
  • Getting the session back. claude --teleport pulls a cloud session into your local terminal. It needs a clean git state, the same repository, the branch pushed and the same claude.ai account.
  • GitHub access. Cloud sessions reach your repositories through the Claude GitHub App or a token that /web-setup (a command you run in the terminal) sends to Anthropic; it sends your local gh (GitHub command-line tool) token. The proxy that holds your credential does not limit which branches a push can update. Use GitHub branch protection or rulesets (rules on which branches may be changed and by whom) for that.

To run an agent away from your laptop with OpenCode, run it yourself in your own container or virtual machine. That is your own infrastructure and your own responsibility.

A local Ollama model keeps prompts on your machine, though web or tool calls the agent makes may leave it. If your data agreement rules out third-party processing, ask whether this local route is allowed.

5. Environments

An environment is a saved configuration for cloud sessions: network access, environment variables, a setup script and network secrets. A first-time setup creates one called Default, with Limited access.

Network access levels:

Level What the VM can reach
None No internet (the Anthropic API, the GitHub proxy and enabled connectors still work)
Limited A default allowlist (a list of the only hosts permitted) of package registries, GitHub and cloud SDKs, plus domains you add
Full Any host

Pick the narrowest level that lets the task finish.

  • Setup scripts: a setup script is a Bash script that runs once before Claude starts, to install what the task needs. Installs need network access, so None blocks them.
  • Environment variables versus network secrets: environment variables are readable by any command Claude runs. Network secrets are the safer option where possible: the key stays outside the VM, and a proxy adds it to requests to hosts you list.
  • Preinstalled tools: common programming tools are present. No R, conda or bioinformatics tools are listed, so ask Claude to run check-tools (a shell command on the cloud machine that reports tool versions; you ask Claude to run it, you do not type it with /) to see what is there.

6. Permission modes in the cloud

A permission mode says how much the agent may do before asking you. Cloud sessions offer Accept edits, Plan and Auto. There is no Manual or Bypass mode there. You pick the mode in the dropdown.

Use Plan for anything you do not already understand, and read the plan before it edits. You can also plan locally with claude --permission-mode plan, commit and push the plan, and then start claude --cloud.

7. Limits and failure modes

  • A fresh machine every time. An idle session stops and its VM is taken back. Commit and push work you want to keep.
  • Size. A cloud machine has limited CPU, memory and disk. Heavy jobs may be stopped.
  • Shared usage. Cloud work counts against the same plan limits as all your other Claude Code use.
  • GitHub comments under your name. Claude can reply on pull requests under your GitHub name, marked as from Claude Code.

8. Review what comes back

The result is a branch. Treat it like a stranger’s pull request: it may be fine and it may be wrong.

  1. Read the diff (the list of changed lines) as you would any other.
  2. Look for accidents in the diff: committed data files, absolute paths, sample IDs in a test or a comment, a .env, a notebook saved with outputs (a notebook is a Jupyter document mixing code and results; its saved outputs are the tables and plots stored inside the file).
  3. Run the tests locally, on your machine.
  4. Only then run the script on your data, locally or on the cluster, under your data agreement. The cloud agent never saw that data and never ran that step.

A green test in the cloud is a claim to verify. A test passing on mock data tells you the script runs; your real data is the next check, run locally.

Exercise: the safe-to-send checklist

No cloud account, GitHub account or model needed, and no repository to clone. The tree is a text file in this course’s exercises folder. Open tree.txt, a mock repository tree (every name is invented).

  1. Mark each path that must not reach anything a cloud session can see. Say whether it needs removing from history (it is already committed) or only ignoring, and write one reason each.
  2. Write the .gitignore lines that would have stopped it.
  3. Draft a ticket-style prompt for one low-risk task: update docs/usage.md, or add a missing-column test to scripts/validate_samplesheet.py. Include the problem, the expected result and a check that uses only data/mock/.
Answer key (some entries depend on your data agreement)
  • Every path under “Paths to remove” is committed, so remove each one from history before you push anything a cloud session can see. The ignore lines further down only prevent a repeat.

Paths to remove:

  • .env: a secret. It was already committed, so remove it from history and replace the token; ignoring it helps only from now on.

  • samplesheet_real.csv: identifiers and genotype calls.

  • data/raw/ and data/processed/: real reads and real counts.

  • notebooks/01_qc.ipynb and notebooks/02_diffexp.ipynb: outputs saved inside them contain real sample IDs, tables and plots. Clear the outputs, or keep the notebooks out.

  • results/ (including de_genes.csv and pca_real_samples.png): results.

  • logs/slurm-482913.out: real sample IDs and cluster paths.

  • notebooks/.ipynb_checkpoints/: autosave copies of the notebooks, with the same saved outputs.

  • Fine to send (they hold no real data): README.md, environment.yml, samplesheet_template.csv, config/params.yaml (check it for real paths), data/mock/, docs/, scripts/, tests/.

Ignore lines that would help:

.env
.env.*
samplesheet_real.csv
*.fastq.gz
data/raw/
data/processed/
results/
logs/
.ipynb_checkpoints/

Add a rule for notebooks too (for example, a pre-commit hook, a script git runs automatically before each commit, that clears outputs), because .gitignore alone cannot strip outputs from a notebook you do want to commit. Likewise, .gitignore only stops files that are not yet tracked; anything already committed stays in history until you remove it properly, and rewriting history is its own careful job.

Sample prompt:

Problem: docs/usage.md does not mention the --strandedness option added in v0.3.
Expected: a short section with the option, its allowed values, and one example
command using data/mock/ only.
Check: the example command in the new section runs on data/mock/counts_mock.tsv. Only edit docs/usage.md.

A prompt line is a request to the model. The safe version of this repository has no real data folders to read.

What to remember

  • Cloud sessions are for drafting scripts and documentation; analysis stays on your machine or the cluster. Real data, controlled data, sample sheets with identifiers, genotypes and results stay out of a cloud session and its repository.
  • Your repository contents, prompts and session transcript go to Anthropic, and network level None may still let data exit the VM.
  • Return is a branch: read the diff, look for stray data, run the tests locally, then run on your data where it lives, under your data agreement.
