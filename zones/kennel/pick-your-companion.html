Pick Your Companion

  • Goal: you will set the model and the effort on purpose, including for a subagent, and compare two settings on your own task.
  • Before you start: Recruit the Beast. Adopt the Pet helps with the OpenCode tab.
  • Time: about 15 minutes. The exercise is a worksheet and needs no model.

The companions in the Kennel are models. The harness is the program that runs a model and its tools. This page covers which companion to bring to which job, and how hard to make it think. Model names, aliases and defaults change often, so check your own tool for the current ones.

Words to know

  • Model tier: a size class of model. A smaller one is faster and cheaper; a larger one is more capable and costs more.
  • Alias: a short nickname (such as sonnet) that the tool maps to a concrete model version.
  • Effort: how much the model thinks before each step.
  • Subagent: a helper the main agent starts with its own fresh context. It does a side task and returns only a summary. To delegate is to hand it a task.
  • Token: a chunk of text, the unit that usage and cost are counted in.
  • Context: the text the model can see right now.
  • Frontmatter: the small settings block at the top of a Markdown file.
  • Pin: name one exact model version so it never silently changes.
  • Inherit: use whatever the parent is using.
  • Prompt cache: a short-term store that makes re-reading an unchanged conversation cheaper.
  • Compacting: replacing the conversation history with a short summary.

1. Two dials

  • Model: what the companion knows and can do.
  • Effort: how much it thinks per step. Lower effort means fewer and terser tool calls (the actions the agent takes, such as reading a file or running a command); higher effort means more thoroughness.

Tuning effort is often a better lever than switching models.

2. How to set them

  • Claude Code
  • OpenCode + Ollama

Model. The aliases are default (clears an override and names no model), best (same as opus), fable, sonnet, opus, haiku, sonnet[1m], opus[1m] (the [1m] forms ask for a longer context window), and opusplan (opus in plan mode, then sonnet for the execution). Plan mode is a mode in which the agent proposes a plan and edits nothing until you approve it. On the Anthropic API, opus, sonnet and haiku map to the current 5.5 versions; other providers can resolve the same alias to older versions.

Way How Note
In a session /model <alias or name> alone, it opens a picker; Enter saves it as your default, s keeps it for this session only
Per launch claude --model <alias or name>
Environment ANTHROPIC_MODEL
Settings file model field

For results that must be reproducible (a lab pipeline, course material), pin a full model name such as claude-opus-5-5, because an alias moves when a new version ships. The variables ANTHROPIC_DEFAULT_OPUS_MODEL, ANTHROPIC_DEFAULT_SONNET_MODEL, ANTHROPIC_DEFAULT_HAIKU_MODEL and ANTHROPIC_DEFAULT_FABLE_MODEL pin what each alias means.

Effort. Set it with /effort, claude --effort, the environment variable CLAUDE_CODE_EFFORT_LEVEL, or the effortLevel setting. The levels are low, medium, high, xhigh and max, and which ones exist depends on the model. The default differs by model and by surface: for Sonnet 5.5 it is medium in Claude Code and high on the API. Run /effort in your own tool to read yours.

Per skill and per subagent. Skill files and subagent files both take model and effort in their frontmatter.

  • Skill: model takes the same values as /model, or inherit. A skill’s model and effort apply for the rest of that one turn and are not saved. Its effort overrides the session level but not CLAUDE_CODE_EFFORT_LEVEL.
  • Subagent: model takes sonnet, opus, haiku, fable, a full model ID, or inherit. effort takes low to max. If the subagent’s model differs from the main one and you give no effort, the session level does not apply to it, so set it.
  • Which model a subagent gets, first match wins: the per-call model parameter, then the definition’s model, then the environment variable CLAUDE_CODE_SUBAGENT_MODEL, then the main conversation’s model.

A subagent is a Markdown file with frontmatter in .claude/agents/ (project) or ~/.claude/agents/ (yours):

---
name: log-reader
description: Reads long pipeline logs and reports only failed tasks with their error lines.
model: haiku
effort: medium
---
Read the logs you are given. Return: task name, exit status, the first error line.
Quote lines exactly. If something is unclear, say so.

A tools field can also limit what the helper may use. The sub-agents page in Lore has the exact syntax.

This sketch uses medium because Haiku 5.5 at low is more likely to skip a search, stop early or skip a check. For reading logs, catching every failure is the point.

  • /models picks a model for the current session only; the config file is unchanged.
  • opencode run --model provider/model-id sets it for one run. The format is provider/model-id, with an optional #variant such as #high. IDs are case-sensitive.
  • The model key in opencode.json (or opencode.jsonc) sets your default.
  • An agent can have its own model key. A subagent with no model inherits the parent session’s model. The frontmatter example is mode: subagent plus model: anthropic/claude-sonnet-5-5#high.
  • A local Ollama model is selectable like any other, for example ollama/gemma3:4b.

3. Starting points

Start from the tiers and the table below, and test each row on your own jobs. The four tiers, in order of capability:

  • Haiku: fastest replies and lowest cost; suited to subagent tasks.
  • Sonnet: everyday coding and agent work.
  • Opus: complex agentic coding; most workloads start here.
  • Fable: the hardest, long-running work.
Job Start with Effort Why
Most everyday work, no better information Opus the tool’s default most workloads start here
Bulk reading, classifying or extracting with output you can check Haiku, often as a subagent medium, or low if you re-run failures cheap per item; a checker catches errors
Exploratory reading (“where is X handled?”) a subagent low or medium the main context stays clean; only a summary returns
Planning a change consider Opus or Fable medium to high a bad plan makes every later step wrong
Mechanical edits with tests that fail loudly Sonnet medium the tests do the judging
Hardest multi-file change, or unfamiliar science Opus or Fable high, then up only if a check shows a gain a stronger model may know more

4. When the output is not good enough: the upgrade ladder

Climb one rung at a time and re-check after each.

  1. Add a way to verify. A test, a script, a count against an independent tool, a second look that does not share the first one’s blind spot. Without it you cannot tell whether the next rungs helped.
  2. Raise effort one level.
  3. Change the model to the next tier up.

Cheap-then-retry: if outcomes are checkable (tests, or a verifier, which is a separate check that tests the output), run at low effort and re-run only the failures at higher effort. A checker that passes bad work lets failures through, and a failure costs two runs of waiting time.

Compare cost per finished task, because failed tasks still cost money and a few hard tasks can carry much of the bill.

5. Delegation hygiene

  • Keep the expensive model’s context lean. Sending bulk reading to a subagent keeps that reading out of the main conversation.
  • Spot-check summaries. A subagent returns only a summary, and summaries omit and distort. Ask for exact quotes or file paths and open two yourself. Many subagents returning long answers can also fill the main context again.
  • State your rules in the delegation prompt. The built-in Explore subagent (a read-only search helper) and Plan subagent (a read-only research helper used in plan mode) skip CLAUDE.md, the instructions file the tool loads at session start. A rule like “never touch raw/” must be written into the task you hand them. Custom subagents load CLAUDE.md unless set to skip it.
  • Switch models at a quiet moment. Switching model mid-conversation can change prompt-cache behaviour, and the tool may ask you to confirm.
  • Change effort between sessions when you are comparing. Changing top-level effort mid-session also invalidates the cache.

6. Measure on your own task

Pick one small real task that has an outcome check (a test that passes, a count that matches).

  1. Choose two settings to compare, for example the same model at medium and high. Change only one thing.
  2. For each, start a fresh session, run the task three times, and record pass or fail from the outcome check.
  3. After each run, open /usage and note the “Usage by model” block. The dollar figure is an estimate computed locally at list price, and on a subscription you may see plan usage bars instead. /usage resets on /clear.
  4. Compare cost per passing run. Three runs is a small sample: it can expose a big difference, and a small one needs more runs.

7. What you gave up

Choosing wrongly costs you in both directions. Too small or too low: the companion loses the thread, skips checks or stops early, and you redo the work, often after you have already trusted it. Too big or too high: the same job costs more and runs slower, and you may not notice because the answer looks fine. The checks above are how you notice either mistake.

8. Other model families

The ideas above carry over to other families; the names do not. Mistral is one example:

  • Models: Ministral 3 comes in 3B, 8B and 14B, and Mistral Small 4 is also open-weight; both are Apache 2.0. Check Mistral’s models page for current names and deprecation dates.
  • Harness: Mistral Vibe is an open-source terminal coding agent (Apache 2.0) with four approval modes. Its config file is ~/.vibe/config.toml.
    • ask: asks before any tool.
    • accept-edits: the default; applies file edits without asking, and still asks before shell commands.
    • smart-approve: see the Vibe docs for how it decides.
    • auto-approve: for trusted, sandboxed environments only.
  • Trusted folders: Vibe loads project config only from folders you have trusted. Start in ask until you trust the project.
  • Local models: Vibe works with any model served behind an OpenAI-compatible API, such as vLLM, llama.cpp, LM Studio or Ollama. Check the Vibe docs for the Ollama setup.

When you switch families, redo the worksheet below. A tier ladder built on one vendor’s models does not carry over name for name.

Exercise: assign six jobs

No model needed. For each mock job, write down a model (Haiku, Sonnet, Opus or Fable), an effort (low, medium, high) and whether you would use a subagent, then open the key.

  1. Rename 200 sample IDs in a samplesheet to a new scheme, given a mapping table.
  2. Summarise the methods section of one paper into five bullets for your lab notes.
  3. Debug a Nextflow stage that fails on one sample and passes on the others.
  4. Classify 5,000 free-text tissue labels into 12 categories, with 200 hand-tagged rows to check against.
  5. Plan a refactor of a 600-line QC script that three other people depend on.
  6. Explain an error message you have not seen before.
Answer key (several answers are defensible)
  1. Probably no model at all. A mapping table and a script do this exactly, and a script cannot invent an ID. If you use a model, Haiku at low or medium, with a diff or count check; no subagent needed.
  2. Sonnet, medium, no subagent. The text is short, so there is no context to protect. Check two claims against the paper yourself.
  3. Sonnet at medium, raised to high or Opus if the first attempt fails and a test says so. Keep it in the main conversation, because the debugging needs the history. Add a failing test first (rung 1).
  4. Haiku, a subagent or a batch script, medium. The 200 hand-tagged rows are your outcome check; re-run only the rows that disagree at a higher setting. Spot-check a sample of the rest.
  5. Opus, high, in plan mode, main conversation. A weak plan is expensive downstream and other people depend on the script. Ask for a test plan too.
  6. Sonnet, low or medium, no subagent. It is a short, checkable question: try the suggested fix. Escalate when the explanation does not hold up.
Check what model and effort your tool is using right now (/model, /effort) and write them down.
Run the same small task at two settings and compare the result and /usage.
