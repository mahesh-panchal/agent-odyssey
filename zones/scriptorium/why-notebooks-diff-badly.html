Why Notebooks Diff Badly

Scribes in the Scriptorium keep notebooks, and every page is stuffed with outputs and images. Reviewing one change means wading through all of it. Find out why, then find the single line that mattered.

  • Goal: you will explain why a one-line change to a notebook produces a noisy diff, and name four ways to make the change reviewable.
  • Before you start: Save Point (for git diff), and two tiny mock notebooks, before.ipynb and after.ipynb (about 2.5 KB each). They are mock files that omit cell ids (the unique id that newer notebook files give each cell), so they are not strictly valid notebooks. Save both into an empty folder.
  • Time: about 15 minutes.

A notebook is a JSON file

You need this before an agent edits a notebook for you: if you cannot see what changed, you cannot review it. A .ipynb file is a JSON document with metadata, nbformat, nbformat_minor (the notebook file-format version numbers) and a list of cells. A code cell stores its source, and also an execution_count and its outputs. A plot is stored inside the file as a base64 string (the image bytes written out as plain text). Source and outputs share one file, so any run rewrites lines next to the code.

This is what git sees, with or without an agent. The two mock notebooks differ by one real change: the cutoff 30 became 40. Compare them:

diff before.ipynb after.ipynb
5c5
<    "execution_count": 3,
---
>    "execution_count": 7,
8c8
<     "print(len([r for r in reads if r >= 30]))"
---
>     "print(len([r for r in reads if r >= 40]))"
15c15
<       "3\n"
---
>       "2\n"
21c21
<       "image/png": "AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGx...
---
>       "image/png": "AAMGCQwPEhUYGx4hJCcqLTAzNjk8P0JFSEtOUV...

Four spots changed, and one of them is the code. The rest is the run counter, the printed result and an image blob. A real notebook has more cells and bigger images, so the code change is harder still to find; git diff --stat shows how large a notebook diff is.

The risk is the same with a coding agent as with a human: a reviewer who cannot find the code change may approve without reading it.

Four ways to make changes reviewable

Each option moves the noise somewhere else. Pick by what your team can adopt.

  • nbstripout: strips outputs and some metadata when git stores the notebook. Outputs stay in your working file. A filter is a program git runs on a file as it stores it. Cost: each collaborator runs nbstripout --install themselves, because git does not copy filter settings when someone clones the repository.
  • jupytext: pairs the .ipynb with a .py (the py:percent format suits code). You review the .py and outputs stay in the .ipynb. Cost: two files to keep in sync.
  • nbdime: a notebook-aware diff, with nbdiff in the terminal, nbdiff-web in the browser, git integration and a merge driver. Cost: everyone reviewing needs it installed.
  • marimo: stores notebooks as pure Python, so ordinary git diffs work. Cost: a different notebook tool from Jupyter. marimo convert your_notebook.ipynb > your_notebook.py converts an existing notebook.

Review the code cells

Whatever you choose, the review habit is the same:

  • Look at the source cells. Treat outputs as something to regenerate.
  • Run git diff --stat before committing and look for a notebook that grew by megabytes.
  • An output in a diff shows that something ran once; a re-run shows whether the code produces it.

With an agent

  • Claude Code
  • OpenCode + Ollama

Claude Code reads a .ipynb with all its cells and outputs, and an output-heavy notebook fills the context window (the text the agent can hold at once). When an agent edits a code cell, expect that cell’s saved outputs and execution count to be cleared, so the diff shows lost outputs as well as new source.

nbstripout is a git filter, so outputs stay in the working file and the agent still reads them. To keep the agent on the code, strip outputs from the working copy (nbstripout’s pre-commit mode does this) or point the agent at the paired .py. Check the docs for your version.

The idea is the same: review the source cells. Check OpenCode’s docs for how it handles notebook files.

Lore

Further reading. Optional.

  • The Notebook file format: nbformat, docs. Why read: it is the spec showing that a notebook is JSON holding outputs, execution counts and base64 images, which explains the noisy diffs.
  • nbstripout: nbstripout project (GitHub), repo. Why read: it strips outputs from a notebook with a Git filter set up by nbstripout --install, so Git never sees them.
  • Jupytext: jupytext project (GitHub), repo. Why read: it pairs an .ipynb with a plain .py so reviewers diff the code only.
  • nbdime: nbdime project, docs. Why read: it gives notebook-aware diff and merge tools if you must keep .ipynb in Git.
  • marimo documentation: marimo, docs. Why read: it describes a notebook stored as plain Python, so Git diffs show code only; this is the format option the quest compares.
