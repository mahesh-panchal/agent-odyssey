Keep a Living Wiki

A scribe in the mill keeps a ledger that tidies itself. Each new sack of papers is read once, and every page it touches is updated and cross-linked before the scribe sleeps. A traveller wonders what such a ledger can and cannot be trusted with. Learn how it is built and where it can mislead you.

  • Goal: you will describe the three layers and three jobs of an agent-kept wiki, match the pattern to a use case from your own work, and know where it can mislead you.
  • Before you start: RAG and Its Cousins. This is an optional side quest.
  • Time: about 25 minutes. Reading and planning only; you choose whether to build anything afterwards.

The problem: understanding that does not accumulate

Think about the last time you read ten papers on a method, or went through six months of meeting notes. You understood it all at the time. A month later, the understanding lives in your head and in a pile of files, and the next question sends you back to the pile.

You need this lesson now to judge whether a wiki suits your material before you build one. RAG (retrieval-augmented generation) answers that with a lookup: each question searches the pile again, pastes a few passages into the prompt, and starts from scratch. Nothing builds up between questions. If an answer needs five documents stitched together, the stitching is redone every time.

This quest follows Andrej Karpathy’s “LLM Wiki” gist (a short shared text page), which proposes another arrangement. An agent keeps a wiki: a folder of interlinked Markdown pages (plain text files with simple formatting) that it writes and updates as new sources arrive, so the stitching is done once and stays. The gist calls it a “persistent, compounding artifact”. People drop their notes because the bookkeeping is tedious (updating links, rewriting summaries, spotting that two pages now disagree), and an agent does that bookkeeping without getting bored. You keep the parts that need a person: choosing sources, asking questions, and deciding what the findings mean.

The gist is an “idea file”, meant to be handed to your agent so the two of you work out the details together. It describes a pattern and includes no program.

Three layers

  • Raw sources: you add files and nobody edits them afterwards. Papers, clipped web pages, meeting transcripts, run logs, data files. The agent reads them and never changes them, so they stay the source of truth.
  • The wiki: the agent writes it and you read it. Markdown pages: a summary per source, a page per entity (a tool, a dataset, a person, a gene) or concept, comparisons, an overview. The agent owns this folder.
  • The schema: here, “schema” means the rules for the wiki, written as plain instructions (it is not a database schema). You and the agent write it over time. It is one instruction file (CLAUDE.md in Claude Code, AGENTS.md in OpenCode) that the agent reads at the start of every session. It describes how the wiki is organised and what to do on each job, and it is the key configuration file.

The split builds trust. When an answer looks odd, you walk from the wiki page back to the raw source it cites, and the raw source is untouched.

Three jobs

  • Ingest (take a new source into the wiki): copy one source into raw/, then ask the agent, for example, “Ingest raw/paper-1.md following the rules in CLAUDE.md.” The agent reads the source, tells you the main takeaways, writes a summary page, updates the pages for the entities and concepts it mentions, adds it to the index, and appends a line to the log. One source may touch 10 to 15 pages. Ingest one source at a time and stay involved. Batching with less supervision is possible.
  • Query: you ask a question. The agent finds the relevant wiki pages, reads them and answers with citations. A good answer (a comparison table, a timeline, a short report) is filed back as a new page, so your explorations add to the wiki and do not vanish into chat history.
  • Lint: from time to time you ask for a health check. It looks for pages that contradict each other, claims that a newer source has overtaken, pages that nothing links to, concepts that are mentioned but have no page, missing cross-references, and gaps that a web search might fill.

Two small files keep the wiki navigable:

  • index.md: a catalogue with each page, a link and a one-line summary, grouped by category and updated on every ingest. To answer a question, the agent reads the index first and then opens the pages that look relevant. The gist says this avoids building an embedding index at moderate scale (the author’s experience). As the wiki grows, add a search tool.
  • log.md: an append-only diary of ingests, queries and lint passes. Give every entry the same prefix so a simple grep can list the recent ones.

An example schema. Paste it into the instruction file (CLAUDE.md or AGENTS.md) in the wiki folder’s top level, then edit it with your agent:

# Wiki rules
- `raw/` holds sources. Never edit or delete anything in `raw/`.
- `wiki/` holds pages you write. One page per entity or concept; one summary page per source in `wiki/sources/`.
- Every claim on a wiki page ends with a link to the source file it came from. If no source supports it, mark it `(unsourced)`.
- On ingest: read the source, tell me the three main takeaways and wait for my reply, then write the summary page, update affected pages, update `wiki/index.md`, and append `## [YYYY-MM-DD] ingest | <title>` to `wiki/log.md`.
- On lint: list contradictions, unsourced claims, orphan pages and missing pages. Do not fix anything until I say which.

Why you might want this, and what it costs

  • Paste everything into the prompt: fits small collections and needs no setup. You pay in repeated reading each session and a limit at the window size.
  • RAG: fits a large, changing pile where particular passages answer each question. Each question starts from scratch, multi-document answers are re-stitched, and retrieval misses are silent.
  • A wiki the agent maintains: fits material you will return to for weeks or months, where understanding should accumulate and be readable. You pay agent time and tokens on every ingest, you get a layer of text that can contain mistakes, and you spend review time.
  • Notes you write yourself: fit things you want to think through in your own words. This is a perfectly good choice, and the wiki pays off when the bookkeeping is what stops you.

A wiki and search can sit together: a wiki is a good home for the stable understanding, and RAG or search is a good way to reach the raw sources behind it.

Use cases you may recognise

The gist lists personal, research, reading a book, team, competitive analysis, due diligence, trip planning, course notes and hobby deep-dives. Here are some closer to a bioinformatics desk.

  • Literature on one method (say, long-read assemblers or variant callers)
    • Raw sources: papers, preprints, tool docs.
    • Pages: one per tool and dataset, a comparison table, a page of open disagreements.
    • A question: “Which papers compare tool A and B on the same data, and do they agree?”
    • Watch out: preprints mixed with peer-reviewed papers. Ask the agent to record the kind of source on every page.
  • The lab’s pipeline handbook
    • Raw sources: release notes, run logs, meeting minutes, Slack exports.
    • Pages: one per pipeline release, one per known issue, a decision log.
    • A question: “Which runs used release 2.3, and what was wrong with it?”
    • Watch out: private or unpublished material. Exact counts belong to a query tool, not a wiki page.
  • A thesis or long project
    • Raw sources: papers you read, notes on experiments, supervisor meeting notes.
    • Pages: a running thesis page, an open-questions page, one page per experiment.
    • A question: “What did I conclude about batch effects in March, and what has changed since?”
    • Watch out: a wiki that you never open. You will not remember what you did not read.
  • A course, a workshop or onboarding
    • Raw sources: slides, lecture notes, tutorials, tool docs.
    • Pages: glossary, one page per concept, a “things that confused me” page.
    • A question: “Explain the difference between X and Y using only what the course covered.”
    • Watch out: material for fast-moving tools goes stale. Date every source.
  • Reference notes for the tools you use
    • Raw sources: docs pages, GitHub issues, your own gotchas.
    • Pages: one per tool with versions, quirks and a link to the source.
    • A question: “What did we learn the last time this tool ran out of memory?”
    • Watch out: version drift. Record the version on each page and re-check on upgrade.
  • A book or a long series
    • Raw sources: chapters, episode notes.
    • Pages: characters, themes, a timeline, built up as you read.
    • A question: “Where did this thread first appear?”
    • Watch out: spoilers for yourself. Ingest as you read.

To size your own idea, answer four questions in a sentence each:

  1. What sources would go in?
  2. How often do they change?
  3. What question would I ask in a month that I cannot answer quickly today?
  4. Who may read these sources, and where may they be sent?

If the sources fit in one prompt, try that first. If the question is an exact filter or count, ask a query tool. If the sources are sensitive and you would send them to a hosted model, settle your data rules before you begin. If the material is something you want to return to and the answers need several sources joined, the wiki is a good candidate.

Where Obsidian fits

Obsidian is a free note-taking app that opens a folder of Markdown files as a vault. A vault is an ordinary folder, so an agent can read and write it like any other folder, and Obsidian shows whatever is there. Work with the agent on one side and Obsidian open on the other: “Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.” You read, and the agent edits.

A layout that follows the three layers:

my-vault/
  raw/            sources you add (clippings, PDFs, transcripts); the agent never edits these
    assets/       downloaded images
  wiki/           pages the agent writes
    index.md
    log.md
    sources/  entities/  concepts/
  CLAUDE.md       the schema (or AGENTS.md)

Obsidian tools that help:

  • Web Clipper: a browser extension that turns a web article into a Markdown file, so a source can land in raw/ in one click.
  • Graph view: shows the shape of the wiki, with hubs and orphan pages that nothing links to. It doubles as a quick visual check.
  • Dataview: a plugin (an add-on) that queries the properties (named fields in a block at the top of a page). If your schema asks the agent to add them (a source type, a date, a version), you get live tables, such as every page whose status is unsourced.
  • Marp: a Markdown slide format with an Obsidian plugin, for turning an answer into slides. Skip it unless you need slides.
  • Images: fix the attachment folder (for example raw/assets/) and bind a hotkey that downloads a clipped page’s images locally. An agent cannot read a Markdown file with inline images in a single pass, so have it read the text first and look at the images afterwards.

Habits that help:

  • Separate folders: keep the agent’s folder apart from the notes you write by hand. Your own words stay yours, and you can tell at a glance what the agent produced.
  • Git: put the vault under git and commit before each ingest. A commit per ingest gives you a readable diff of what the agent changed and an undo.
  • Read-only sources: make raw/ read-only if your tools allow it. The instruction file is advice the agent can ignore, while file permissions are enforced by the system.
  • Any editor: if you do not use Obsidian, any editor that opens a folder of Markdown files works.

What can go wrong

  • A mistake becomes a fact. If the agent misreads a source, the error lands on a page, and later pages cite that page. The cost grows with each ingest. Require a source link on every claim, skim the diff of every ingest, and use lint to hunt for unsourced claims. One source at a time makes the skimming practical.
  • The agent edits what it should only read. Keep sources immutable and check it with git.
  • Clipped pages can carry instructions. A web page you clip may contain text aimed at your agent, and the agent reads it during ingest and then writes files. Review the diff, restrict what the agent may run, and keep an agent with write access away from sources you do not trust.
  • Sources leave your machine. With a hosted model, every source you ingest is sent as prompt text. For unpublished results, patient-linked data or anything under an agreement, check the rules first. A local model through Ollama keeps text on your machine, but ingest asks for reading, summarising and editing several files in one go. Try one short, harmless source first.
  • Cost and time grow with the wiki. Each ingest reads the index and several pages, and then writes several. Watch your usage in the first week.
  • Scale. As the wiki grows, add search or another layer on top of the index.
  • You may not learn it. A wiki you never open does little for your own understanding. Read it, correct it and argue with it.
  • Exact answers. Counts, filters and joins over tables belong in a query tool, not in prose pages.

Choose your setup

  • Claude Code
  • OpenCode + Ollama

Put the schema in CLAUDE.md at the root of the wiki folder. Start a session there, and ask the agent to read the schema and propose the folder layout before it writes anything. For the first ingest, ask for a plan and approve it before the agent writes. Tighten the schema with whatever you correct. Keep ingest, query and lint as separate short sessions, since the wiki itself is the memory that carries over.

Put the schema in AGENTS.md at the root of the wiki folder (OpenCode also falls back to CLAUDE.md). With a local model, start with a handful of short, non-sensitive sources and check each page against its source, because a small model is more likely to drop or garble details. If a model struggles with the multi-file edit, ask it to do the ingest in steps: summary page first, then one entity page at a time.

Battle: the wiki

Answer the four sizing questions for one real collection of yours (sources, how often they change, the question you will ask in a month, who may read them and where they may be sent). Write one sentence saying whether a wiki, RAG, a single prompt or a query tool fits best.
Draft a schema (instruction file) of five lines or fewer for that collection: what the agent must never edit, what every claim must carry, and what it must ask you before writing. Do not run it yet; read it aloud to a colleague and see what they would add.
