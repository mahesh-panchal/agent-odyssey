Handoff Notes

You wake at the mill with a fresh Astral and a half-finished job. It knows nothing of yesterday except what loads by itself or lies written down, and yesterday you wrote nothing. The mill keeps a ledger of notes for exactly this gap. Learn what belongs in it, and the next visit starts where the last one stopped.

  • Goal: you will list the five things that carry knowledge into a fresh session, and write a short handoff note a fresh session can act on, with what was checked kept apart from what was not.
  • Before you start: Capture Ideas Mid-Task. Commands here are Claude Code commands.
  • Time: about 15 minutes.

You stop work on Friday with a half-finished refactor. On Monday you open a new session (one conversation with the agent, which has its own context: the text it can see right now). Each session begins with a fresh context window and no conversation history from before, so the new session does not know your goal, what you tried, or what you checked.

You need this lesson now because a fresh session is where the earlier lessons’ habits pay off: whatever it should know has to cross the gap in writing.

Five things that cross the gap

  1. The instructions file (CLAUDE.md in Claude Code). A file you write that is loaded at the start of every session. Good for stable facts and conventions: how to run the tests, which folders are off limits.
  2. Auto memory. Notes the harness (the program around the model) writes itself, from your corrections and preferences. In Claude Code, /memory lists and opens them.
  3. Files in the repository (the project folder under version control): code, tests, a README, and, if you keep one, a progress or handoff file.
  4. Git history. A commit is a saved snapshot of the project with a message you or the agent write. The list of commits shows what changed and when. It is durable unless someone rewrites it (with git commands that replace past commits, such as git rebase, git commit --amend or git push --force), and unpushed commits are local only.
  5. Your handoff note. A short file about the state of one task, written for the next session.
What Goes where Lifetime Who writes it Trust
Stable rules and conventions Instructions file Until you edit it You High if short and checked
Preferences the harness picked up Auto memory Until deleted The harness Medium: it can be wrong
What the files say now Files in the repository Until edited or deleted You or the agent Medium: files can be stale
State of one task Handoff note Until the task is done You, or the agent drafts and you review Only as good as your review
What changed, and why Commit messages in git history Durable unless rewritten; local until pushed You or the agent Reliable for what changed; the why is only as good as the message

Memory the harness wrote can be wrong, and a wrong line is loaded again every session. This is context poisoning: a wrong statement enters the context and later answers build on it. Read /memory and check any claim against the source before you rely on it.

Three habits help a long task: keep a progress notes file, make git commits with descriptive messages so bad changes can be reverted, and begin each session by reading the progress file and the recent git log, then run a basic check before new work.

What a good handoff note contains

Keep it short, so reading it costs less than rediscovering the state. Point to files and commands, and let the next session run them for fresh output.

  • Goal in one line.
  • Current state: branch, last commit, what runs and what does not.
  • Decisions and the reasons, including options you rejected.
  • Verified, and how; not verified. Two separate lists. For each verified item, the command and what it showed.
  • What failed and should not be retried.
  • Next steps, in order.
  • Pointers: file paths, commands, job IDs, work directories.
  • Open questions and parked ideas (ideas you decided to leave for later).

Mock example

This is a mock handoff note for a mock task. The file names and numbers are invented.

# HANDOFF: qc_filter.py refactor (mock example)

## Goal
Replace the per-read loop in qc_filter.py with a vectorised version, same output.

## State (git branch refactor-qc, last commit a1b2c3d "qc: add vectorised mean quality")
- New function mean_qual_fast() is written and called from main().
- Old function mean_qual() is kept for comparison. Do not delete yet.

## Decisions
- Keep both functions until all samples are compared (a bug here would silently change which reads pass).
- Threshold stays at mean Q20, as in the lab protocol.

## Verified
- tests/test_filter.py: ran `pytest -q`, 6 passed.
- sample_A: `diff <(python qc_filter.py A.fq) old_out/A.txt` gave no output.

## Not verified
- Samples B and C have not been compared with the old output.
- Reads shorter than 30 bases: no test covers them.
- Speed gain: not measured.

## Failed, do not retry
- Using numpy on the raw quality string: wrong values for the Phred offset. Convert to integers first.

## Next steps
1. Compare B and C against old_out/ with the same diff command.
2. Add a test for a 10-base read.
3. Only then delete mean_qual().

## Open questions / parked
- Should the threshold be a command-line option? Parked for a later task.

Where to put it, and how to start the next session

Put the note in a file the next session can find. Two options:

  • A file in the repo, such as HANDOFF.md, if the team should see it.
  • A gitignored ordinary file you point to, if it is personal. This is the simpler choice.

A CLAUDE.local.md file in the project’s top-level folder (add it to .gitignore) holds private per-project preferences and loads after CLAUDE.md. It exists only in the worktree (separate checkout folder) where you created it.

Anything loaded every session takes room in the window, so keep a handoff note out of CLAUDE.md and remove it once its task is done.

Write the note before you run /clear (which starts a new empty conversation), because /clear drops the conversation. Pairing the note with a commit leaves a matching record in git.

Then start the new session with a prompt like this:

Read HANDOFF.md, then tell me your understanding before changing anything.

The agent restates the goal and state in its own words, and you compare that with what you know. This is a cheap comprehension check: it can catch a misreading of the note. The restatement comes from the same model that read it, so the note’s claims still need checking against the source.

You can ask the agent to draft the note at the end of a session. Review it yourself, since a draft can overstate what was verified (“all tests pass” when none were run in that session).

Commands:

  • /memory: see memory files.
  • /clear: new empty conversation.
  • /resume and claude --resume: reopen an earlier session.
  • claude --continue: the most recent session in this directory.
  • /export: writes the conversation as plain text for a person to read. Transcripts are long, so write a short curated note yourself.

Commands: /new (alias /clear), /sessions (aliases /resume and /continue), /compact and /export. The handoff note itself is just a file, so the practice carries over. Check OpenCode’s documentation for how it loads project instructions, and keep the note short if your local model has a small window.
