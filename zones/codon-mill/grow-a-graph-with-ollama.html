Grow a Graph with Ollama

  • Goal: you will build a small knowledge graph from twelve mock lab notes with a local model, query it, compare it with simple RAG, and learn what LightRAG and Microsoft GraphRAG ask of an Ollama setup.
  • Before you start: RAG and Its Cousins, and Adopt the Pet (Ollama installed and running). Python 3 on your path; the scripts use only its standard library. This is an optional side quest.
  • Time: about 30 minutes, most of it waiting for the model. Everything stays on your machine, and the notes are mock data.

Words first

  • Simple RAG: embed every note, embed the question, keep the k closest notes, and ask the model to answer from them.
  • Knowledge graph: facts stored as (subject, relation, object) triples. Things are nodes and the links between them are edges.
  • Hop: one step along an edge from one entity to a linked one.

Set up

mini-rag holds ollama_min.py (two helpers), rag.py (simple RAG), graph.py (a hand-made graph RAG) and notes/ (twelve short mock notes, 233 words in all). Save the folder anywhere. If the link is not available, ask your agent to recreate it from the descriptions below.

Pull an embedding model and pick a chat model you already have.

ollama pull nomic-embed-text
export CHAT_MODEL=gemma4:12b-mlx      # or any chat model you have pulled
cd mini-rag

The scripts read three environment variables: CHAT_MODEL, EMBED_MODEL (default nomic-embed-text) and OLLAMA_URL (default http://127.0.0.1:11434). Ollama’s default context is small, so the scripts send each request with num_ctx set to 8192 and you do not have to restart the server.

Open notes/ and read a few. They are fictional: two sequencers (Orion and Vega), two projects (Heron and Kelp), two pipeline releases, and some distractors such as the lunch rota. One question needs a chain of four hops: Project Heron studies samples S31 to S36, run R7 loaded those samples, run R7 used pipeline release 2.3, and release 2.3 has a known bug.

Step 1: simple RAG

rag.py is simple RAG in about thirty lines.

python3 rag.py "Does project Heron need to re-analyse its data because of a known pipeline bug?"

With the default -k 3 the run printed:

Retrieved:
  0.668  pipeline-2-4.txt
  0.653  pipeline-2-3.txt
  0.644  project-heron.txt

Answer:
The notes do not contain the answer.

The notes that hold the answer were in the folder, but the run log that connects Heron’s samples to pipeline 2.3 ranked fourth. Try -k 5:

  0.668  pipeline-2-4.txt
  0.653  pipeline-2-3.txt
  0.644  project-heron.txt
  0.549  run-r7.txt
  0.528  run-r8.txt

Answer:
Yes, project Heron needs to re-analyse its data because the primary analysis of run R7 used pipeline release 2.3, which has a known bug that double-counts duplicate reads.

Then try --all, which skips retrieval and pastes every note into the prompt. It also gave a correct answer. With twelve short notes, the window holds everything.

Step 2: build the graph

graph.py build sends each note to the chat model and asks for (subject, relation, object) facts. It uses Ollama’s structured outputs: the request carries a JSON schema in the format field, so the reply is JSON in the shape the script expects. Temperature 0 gives more deterministic output, and the helper sets it.

python3 graph.py build
python3 graph.py show

The run printed saved 67 facts, and the build took 1 minute 20 seconds for twelve notes. A sample of what show printed:

Run R7 --loaded onto--> Orion    [run-r7.txt]
Run R7 --used--> Pipeline 2.3    [run-r7.txt]
Pipeline 2.3 --has bug--> double-counts duplicate reads    [pipeline-2-3.txt]
Project Heron --studies--> S31    [project-heron.txt]
Orion --looked after by--> Dana Okafor    [orion.txt]
You --bring--> own cup    [lunch.txt]

Read the whole list. Most facts match their notes. Two did not: the lunch note produced You --bring--> own cup, which is not a fact about anything in the lab, and one name came back with a stray leading space, which would split a single entity into two nodes (the script now strips names when it loads them). Extraction is a model’s reading of your text, so a graph is a second thing to check. Every fact carries the note it came from, so you can.

Step 3: ask the graph

graph.py ask does three things. It finds starting entities (names that appear in the question, plus the three closest by embedding). It walks outward two hops along the links. Then it hands the collected facts and their source notes to the model.

python3 graph.py ask "Does project Heron need to re-analyse its data because of a known pipeline bug?"
Starting entities: ['pipeline 2.3', 'pipeline 2.4', 'project heron']
Collected 40 facts from 8 notes: freezers.txt, meeting-march.txt, pipeline-2-3.txt, pipeline-2-4.txt, project-heron.txt, project-kelp.txt, run-r7.txt, run-r8.txt

Answer:
Yes, Project Heron needs to re-analyse its data because Run R7, which loaded the samples for Project Heron (S31 to S36), used Pipeline 2.3, which has a known bug that double-counts duplicate reads.

Notes used:
- [pipeline-2-3.txt]
- [project-heron.txt]
- [run-r7.txt]

The wording of the answer differs a little from run to run even at temperature 0, so yours will not match word for word.

What we saw

With gemma4:12b-mlx for chat and nomic-embed-text for embeddings:

  • Simple RAG missed at k=3 and succeeded at k=5. The run log was not among the top three notes. Raising k fixed it, at the price of more text in the prompt.
  • Putting everything in the prompt also worked, because the collection is tiny.
  • The graph walk reached the run log without a bigger k, because the link from Heron’s samples to run R7 is an edge. It also pulled in 40 of the 67 facts and 8 of the 12 notes. A bigger collection needs a smaller hop count or a ranking step.
  • The graph took a minute and twenty seconds to build for 233 words and needs a model good enough to extract facts. Embedding twelve notes for simple RAG takes seconds. Build cost grows with the size of the collection, and indexing a corpus of about a million tokens took hours in Microsoft’s Graph RAG paper.
  • A whole-collection question failed in all three setups. “Who works in this group, and what does each person do?” got “the notes do not contain the answer” from simple RAG, --all and the graph walk. No note lists a roster. Microsoft’s Graph RAG builds community summaries for such questions; this toy graph builds none.

One question, one model, one run: this shows the mechanics and does not rank the methods or the models.

Try your own questions and compare.

A second model: Mistral’s Ministral 3

Swapping the chat model is a one-line change (export CHAT_MODEL=...). ministral-3:8b from Mistral is 6.0 GB on Ollama, supports tools and has an Apache 2.0 licence. Retrieval is the same, since the embedding model is the same. The graph is rebuilt by the new model, so its walk differs: 25 facts from 7 notes, against 40 facts from 8 notes with gemma4:12b-mlx.

Setup gemma4:12b-mlx ministral-3:8b
Simple RAG, -k 3 “The notes do not contain the answer.” Not enough information in the notes.
Simple RAG, -k 5 Yes, re-analysis needed (correct). No (wrong): says R7 used release 2.4.
--all (every note pasted) Correct. Lists the right facts, then No (wrong).
Graph walk Yes (correct). Collects the R7 and 2.3 facts, then No (wrong).
Whole-collection question Not answered. Not answered.

In the --all run, ministral-3:8b listed R7 using 2.3, which has the bug, then answered No because “no re-analysis was done”. In the -k 5 run it misread the release: the note says 2.3.

The graph build with ministral-3:8b took about a minute, saved 80 facts and returned valid JSON for all twelve notes. show printed a few odd entries: Pipeline 2.3 --has issue fix--> Dana Okafor, a node called Pipeline 2.3 issue, and a User node taken from the safety note. Read show against the notes yourself.

With this model, the right passages reached the prompt in three setups and the final answer was still wrong. Retrieval is one half of the job and the reader model is the other half. Read the notes the answer names and see whether they say what the answer says. Test a model on a few questions whose answers you know before you trust it on new ones. mistral-small (24B, 14 GB) is also on Ollama if you want a larger one to try.

A note on model size

We did not run LightRAG or Microsoft GraphRAG here; this section summarises what their documentation asks of an Ollama setup. Extraction asks a model to produce well-formed JSON for every chunk. With Ollama, Microsoft GraphRAG users “frequently see issues with malformed responses (especially JSON)”. The LightRAG README calls a 30B-parameter model “a reasonable minimum” for local use, and its programming guide says at least 32B. The 12B model here produced valid JSON for all twelve notes, and show lets you judge the facts. If you try a model under about 7B, read the triples before you trust the answers.

Using a real tool with Ollama

graph.py is a teaching toy. Two real projects do this at scale. Check their current docs before you rely on the details below.

LightRAG (github.com/HKUDS/LightRAG):

  • Install pip install "lightrag-hku[api]" (the README also shows uv), copy env.example to .env, and run lightrag-server.
  • For Ollama, the project’s guide wires ollama_model_complete for chat and ollama_embed for embeddings.
  • LightRAG requires at least 32k context tokens, and Ollama’s default is smaller. Set num_ctx to 32768 in code or in a Modelfile. For the server, set OLLAMA_LLM_NUM_CTX in .env. The default context is 4k on machines under 24 GiB of video memory, so check with ollama ps.
  • Use a non-thinking model for extraction. Models slower than about 50 tokens per second may time out on dense chunks.
  • Pick your embedding model before indexing and keep it. EMBEDDING_DIM must equal the model’s output size (the guide uses 768 for nomic-embed-text). Changing the model later means re-embedding everything.
  • The default storage is in-memory files meant for small tests.
  • Server safety: lightrag-server binds to all network interfaces with authentication off by default. On a laptop or shared machine, set HOST=127.0.0.1 before you start it.

Microsoft GraphRAG (microsoft.github.io/graphrag):

  • The commands are graphrag init, graphrag index and graphrag query "..." --method local (or global). Text files go in input/.
  • It can consume a lot of LLM resources. Start with the small tutorial dataset and cheaper models.
  • It calls models through LiteLLM and requires structured JSON output. Users put Ollama behind a proxy and report frequent malformed responses. Check the current docs for an Ollama setup.
  • Check that the embedding vector size in its settings matches your embedding model’s (nomic-embed-text gives 768).

To build a graph over your own notes with Ollama, start with LightRAG on a tiny folder of mock files, then look at the facts it extracted before pointing it at anything real.

Verify the graph

A confident answer built on a wrong link is the failure to look for. A graph gives you a list of facts, each with its source note, to check.

  • Read the extracted facts for a few notes against the notes themselves. Count the wrong ones.
  • Ask the agent or the script to name the notes behind each answer, then open them.
  • Keep a short list of questions whose answers you know, and run it after you change the model, the prompt or the notes.
  • Keep real and controlled data out of this exercise. The same scripts pointed at a hosted model send every note to that provider.

  • Advanced RAG Techniques: Nir Diamant and contributors, repo. Why read: its notebook list includes graph RAG with a local Ollama model and LightRAG, plus chunking and evaluation, though we did not open the notebooks and the repo carries sponsor and book promotions.
