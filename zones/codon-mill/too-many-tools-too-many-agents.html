Too Many Tools, Too Many Agents

The wall of the mill is hung with every tool anyone ever made, and the kennel master’s patter says a good companion carries them all. You tried it, and the companion staggered out under so much iron that it could not find the one it needed. A craftsman picks three and leaves the rest on their hooks. She also asks a harder question: does this job need a crew of helpers at all? Count what each tool costs before you carry it.

  • Goal: you will explain why a large toolset costs context and accuracy, and choose between a single call, a fixed workflow, an agent and a plain script.
  • Before you start: Who Said What. This is an optional side quest.
  • Time: about 20 minutes.

You need this lesson now because every server you connect adds to the window. An agent (a model that runs tools in a loop) has a tool for each action it can take, such as reading a file or searching the web. Each tool has a definition: a name and a description of how to use it. The model needs those definitions in its context window (the text it can see at once) to choose a tool. Too many tools make the agent slower, costlier and less accurate, so the first half of this quest is about keeping the set small. The second half asks whether you need an agent at all.

Tools cost context

Loading every tool definition up front bloats the context. Anthropic reports that a typical five-server setup (an MCP server is a program that offers tools to the agent) can use about 55 thousand tokens in definitions before any work starts, and that choosing the right tool gets worse beyond roughly 30 to 50 available tools.

Tool search (loading a tool’s definition only when the agent needs it) keeps most definitions out of the window and loads a few on demand. Anthropic reports that it typically cuts that overhead by over 85 percent (its own measurement). Treat both figures as rough guides. It pays off from about 10 tools upward, or when definitions are large. Below that, plain tool calling is better.

Tool search (the feature above, which loads a definition only when the agent needs the tool) is on by default for MCP tools. Tool names and server instructions load at session start, and a full definition loads when needed. Extra MCP servers therefore have a small effect on the window. To turn it off, set the environment variable ENABLE_TOOL_SEARCH=false before starting claude. On some older models it falls back to loading everything. Skill descriptions also load at start.

To count your tools, run /mcp to list your connected servers and /context to see how much of the window tools and skills take. Choose your tool set before you start a task.

Check OpenCode’s docs for how it loads tool definitions. Until you know, assume definitions cost context and keep the set small, especially on a local model with a small window.

Keep few, clearly named tools, and remove the servers you do not use.

Single call, workflow, agent, or script

A workflow orchestrates models and tools through paths fixed in code. An agent is a system where the model directs its own process and tool use. Anthropic’s article “Building effective agents” advises starting with the simplest solution that works, and for many uses one well-prepared call is enough. Agents trade speed and cost for performance, and their mistakes compound, so test with limits such as a stopping condition (a maximum number of steps).

  • A plain script: use it when the rule is known. Counting reads, converting a format, running fastqc then trim then align in a fixed order. A pipeline written in a workflow manager such as Nextflow is already a workflow.
  • A single call: use it when you paste the input and want a text answer, such as an explanation of an error.
  • An agent: use it when the next step depends on what it finds, such as debugging a failing run or exploring an unfamiliar repository. Give it a way to check its own work and a limit.

Doing the task by hand is also a fine decision.

Does a team of agents help?

One 2025 preprint (its own tasks and models) compared a single agent with several multi-agent set-ups across six benchmarks. Read the findings as direction, not rules.

  • It depends on the task. On a task that splits into independent parts (financial analysis), multi-agent set-ups did much better than one agent. On sequential planning, every multi-agent variant did worse.
  • A strong single agent leaves little to gain. Once one agent already did well on a task, adding agents gave diminishing or negative returns.
  • Unchecked agents pass errors on. Agents working independently amplified each other’s errors far more than agents whose work a central agent checked.

Start with one agent, measure it, and add agents only for work that splits into independent parts and only if the measurement says it helps.

Battle: choose the smallest option

List the MCP servers and tools in your setup. For each, say when you last used it. Remove or disable one you do not need.
Take one task you gave an agent that had a known rule. Write down the script that would do it without a model.
