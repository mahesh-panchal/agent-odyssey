Memory, Sessions and Usage

Prerequisites: Tokens, Not Letters; The Context Window. Objective: use six terms precisely (token, context window, session context, memory, session usage, context poisoning), and say what to do when a wrong claim has got into a session or into memory. Time: about 15 minutes. Last verified (docs, not run): research/failure-modes.md sources on 2026-11-16 (Claude Code memory, sessions, costs, commands and best-practices docs). Claude Code specific unless stated. Topics in this zone were inspired by Matt Pocock’s course LLM Fundamentals (aihero.dev/llm-fundamentals). The explanations here are our own.

People say “it remembers”, “the session got long” and “I hit my usage” as if these were one thing. They are different things, with different places they live and different ways to reset them. Think of a lab glossary: one term, one meaning.

The glossary

Token. A chunk of text the model reads (a word piece, a character or a byte), not a word. Context limits and usage are counted in tokens. Details are in Tokens, Not Letters.

Context window. Everything the model can see when it writes its next output. It has a size limit, measured in tokens. See The Context Window.

Session and session context. A session is a saved conversation tied to a project directory (stored locally as a transcript file). Its session context is what is in the window right now. The docs say each session begins with a fresh context window and that sessions are independent: a new session has no history from earlier ones.

Memory. Text on disk that is read into a new window at the start of every session. In Claude Code there are two kinds, both loaded at session start:

  • CLAUDE.md: instructions you write (scope = who or where a setting applies: project, user or organisation).
  • Auto memory: notes the harness writes itself from your corrections and preferences. It is per git repository and machine-local, kept in ~/.claude/projects/<project>/memory/ as plain markdown with a MEMORY.md index. Only the first 200 lines or 25KB of MEMORY.md load at start; topic files are read on demand.

Memory is context, not enforced configuration. It also takes room in the window every session. Run /clear and the conversation goes but memory stays. Compaction shrinks a session; it does not create memory.

Session usage. How much of your allowance a session consumes. In Claude Code, /usage shows an estimated session cost (worked out locally from token counts at list price, the published per-token price), plan usage limits and activity stats. /cost and /stats are aliases. The displayed session total resets on /clear; whether allowance already spent on a plan comes back is not documented (our inference: it does not). Two billing worlds exist: with a subscription, the dollar figure is not what you are billed and the plan bars are what matter (plans have rolling and weekly limit windows; see your plan docs, as the docs we read confirm the exact windows only for Teams and Enterprise per-seat allowances); with the API, usage is billed per token, and thinking tokens (the tokens the model spends reasoning before it answers) count as output tokens. This page gives no allowance sizes, because the docs do not state them for the individual plans; see the vendor’s pricing page.

Context poisoning. A wrong or injected statement enters the context and later answers build on it. This is a community term, not vendor documentation. It was coined in the post “How Long Contexts Fail” (2025-06-22) credited to Drew Breunig (the byline comes from a reprint listing; the page text we read did not name him). His example is a game-playing agent whose recorded goals became corrupted with false state. We found no use of this term in Anthropic’s docs; they do describe the same trap in plain words, below.

Why usage climbs

The docs give these reasons. Claude Code sends the whole conversation on every request, and each tool-using step is another request. Caching (a short-term store so repeated text is cheaper to re-read) makes re-reading cheaper but a short question late in a long session still draws on all of it. Large tool outputs (the docs’ example is reading a 10,000-line log) stay in the conversation. Subagents each have their own context, and their requests still count. /compact itself reads the whole conversation. Remedies from the docs: /clear between unrelated tasks, /compact with a focus note, /context to see what fills the window, and keeping CLAUDE.md under 200 lines.

Seeing “rate limited until …” in /usage only means the tool could not fetch plan limits, not that your work is limited.

When a wrong claim gets in

Anthropic’s best-practices guidance is plain: if you have corrected the same thing twice and it is still wrong, a third correction mostly adds to a conversation that already holds two failed attempts for the model to re-read. /clear plus one new prompt that folds in what you learned works better. /rewind can roll back to before the bad turn.

Memory is the sharper danger because it persists. General practice (our inference, not an official instruction): do not let a claim into CLAUDE.md or auto memory until you have checked it against the source, such as the data, the tool’s --help or the paper. If a bad line is already there, open /memory, read what has been written about your project, and delete it.

Commands the docs confirm: /memory (lists memory files, toggles auto memory, opens the folder), /clear (new empty conversation; the old one stays resumable), /compact, /resume and claude --resume (pick an earlier session), claude --continue (most recent in this directory), /usage, /context. Resume restores messages, model and permission mode (what the agent may do without asking), but not flags such as --mcp-config. Transcripts are deleted after 30 days by default.

Not checked: OpenCode’s memory files, session commands and usage reporting. The research for this page covers Claude Code only. If you use a tool with memory, open it (in Claude Code, /memory) and read what it has recorded about a project. Is every line something you could source?
In a session you already have, run /usage and note what dominates: long conversation, big outputs or subagents. If it is not available to you, skip this.
