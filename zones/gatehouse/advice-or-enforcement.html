Advice or Enforcement

A wall of signs hangs in the Gatehouse. Some ask politely and some lock the door, and from across the room they look the same. Learn to tell them apart before you rely on one.

  • Goal: you will sort every control in your setup by whether it advises, asks or enforces, and choose the right one for each risk.
  • Before you start: Guard the Door. A sandbox is an operating-system layer that limits what shell commands can touch.
  • Time: about 15 minutes.

A common mistake is to use advice where a lock was needed. Every control does one of three things.

  • Advises: it puts words in front of the model: an instructions file, Skill text, a line in your prompt. The model reads it and weighs it against everything else in its context. Nothing stops a tool call.
  • Asks: the harness pauses and puts the decision to you: a permission prompt, or an ask rule. It is only as good as your attention at the tenth prompt of the hour.
  • Enforces: code outside the model refuses the action whatever the model wants: a deny rule, a hook that exits 2 (exit code 2 is how a hook says block), a sandbox where one is on. Enforcement has edges too, listed below.

The rule of thumb: advice for preferences, a prompt for decisions you want to make each time, enforcement for things that must never happen.

Control What it does Where it can fail
CLAUDE.md, Skill text, your prompt Advises The model can ignore it.
Permission prompt or ask rule Asks You must read each prompt. A server listed in a project’s .mcp.json file (the shared MCP server list) has its own approval prompt, and -p runs (non-interactive, one prompt) cannot show it.
deny rule Enforces Matches command text, so a reworded command can slip past.
PreToolUse hook, exit 2 Enforces Tool calls only; a crash fails open.
Sandbox Enforces Off by default; shell commands only.
Git history Recovers Prevents nothing.

A hook that exits 0 with no JSON decision adds no control. It expresses no decision, and the normal permission flow runs. A hook can also exit 0 and print a JSON deny decision, which does block.

Deny and ask rules are still evaluated when a hook returns allow. The sandbox’s restrictions still apply if a prompt injection bypasses the model’s decision.

Control What it does Where it can fail
Instructions file, Skill text, your prompt Advises The model can ignore it.
Permission rule with effect ask Asks You must read each prompt.
No matching permission rule Asks Fine, unless you stop reading.
Permission rule with effect deny Enforces Only what the rule matches.
Plugin permission hook (evaluate) Enforces when it denies Runs only for allow and ask.
Git history Recovers Prevents nothing.

An explicit configured deny is final and does not invoke the hook. For OpenCode, check the current docs for an exit-code-2 equivalent, whether throwing in a tool hook blocks a call, sandboxing, and the effect of a local Ollama model before you count on any of them.

Choose by the cost of being wrong

Risk Control Why
Style: prefer snake_case, tidy commit messages Advice A miss costs a review comment.
Pushing to a shared branch Ask You decide each time, with context.
Reading .env or key files Deny rule on Read, plus sandbox or hook for Bash It must never happen; cover each route.
A destructive command you can name Blocking hook Code refuses what it matches.
Fetched text telling the agent to act Least privilege, read-only servers Limit what the agent can do.
An experiment that might wreck your files Git commit, scratch folder Gives you a way back.

Layer them: advice to steer, enforcement for the non-negotiable, git for the day something slips through. Read the diff whatever else you have in place.

Limits for research groups

The same split works for a group that runs agents:

  • Put limits in the system that runs the agent: permission scopes, and spend caps in the metering system (the service that counts each user’s usage and cost). A budget the agent can exceed is not a limit.
  • Name a human owner for each agent duty.
  • Log what an agent did under an identity you can trace.
  • Keep a list of the agents in use, including personal ones connected to mail or files. Institutions can keep one, and a group can keep its own.
  • Use a scoped account, take a backup before granting write or delete access, and name an owner for the machine. An over-privileged agent with shell access can wipe data on a shared lab server.
