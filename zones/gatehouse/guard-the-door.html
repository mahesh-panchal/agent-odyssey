Block Actions with a Hook

Watchman Corin stands at the heavy door and checks every visitor against a list. The list is code, so no one can talk their way past, and your Astral tries every honeyed word it knows. Corin hands you the pen and shows you how to write one line of that list. Write it, then test it.

  • Goal: you will write a hook that refuses a command, and know where a hook’s coverage ends.
  • Before you start: Connect an MCP Server. An exit code is the number a script returns when it finishes: 0 means success, and a hook uses 2 to mean “block”. JSON is a structured text format.
  • Time: about 15 minutes.

Advice can be ignored, and a hook cannot. You need one when a rule must hold whatever the model decides. A hook is a user-defined handler that the harness (the program around the model that runs its tools) runs automatically at a set point, such as just before a tool runs. In Claude Code it can be a shell command, an HTTP endpoint and other kinds, and it receives JSON about the event. An instructions file asks the model to behave. A command hook is ordinary code that the harness runs, so what it decides does not depend on what the model wants.

A hook that refuses

  • Claude Code
  • OpenCode + Ollama

Hooks go in a hooks block in a settings file. For this exercise use .claude/settings.local.json in your scratch folder (yours alone). .claude/settings.json is the committable, shared file, and ~/.claude/settings.json covers all projects.

  1. Save the script below as .claude/hooks/block-drop-table.sh in the project folder and make it executable.
  2. Add the hooks block below to .claude/settings.local.json. $CLAUDE_PROJECT_DIR in it is the environment variable holding the project’s root folder.

A PreToolUse hook fires before a tool runs, and the matcher (the pattern that selects which tool the hook fires for) Bash selects the shell tool:

{ "hooks": { "PreToolUse": [ { "matcher": "Bash",
  "hooks": [ { "type": "command",
    "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-drop-table.sh" } ] } ] } }

The script, from the Claude Code hooks guide. It needs jq (a command-line JSON reader) installed, and it must be executable (chmod +x .claude/hooks/block-drop-table.sh):

#!/bin/bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command')
if echo "$COMMAND" | grep -q "drop table"; then
  echo "Blocked: dropping tables is not allowed" >&2  # stderr becomes Claude's feedback
  exit 2                                               # exit 2 = block the action
fi
exit 0  # exit 0 = no decision; the normal permission flow applies

The hook gets the event as JSON on stdin (the input stream a program reads, here fed by Claude Code), including tool_name and, for Bash, tool_input.command. Exit code 2 on PreToolUse blocks the call, and Claude sees the stderr text (the program’s error output) as the reason. Exit 0 expresses no decision: the call goes through the normal permission flow.

Two behaviours matter for trust:

  • A broken guard fails open. If the script crashes or exits with some other code and prints no valid JSON, the action proceeds on most events. To block on failure, add "onFailure": "block" beside "type" and "command" in the hook’s handler (check that your Claude Code version supports it).
  • Exit 2 blocks on some events only. On PostToolUse the tool already ran and exit 2 shows stderr to Claude. On Notification the exit code is ignored.

OpenCode’s V2 docs describe plugins (files under .opencode/plugins/ or ~/.config/opencode/plugins/) that can register hooks. To refuse an action, use the permission hook, ctx.permission.hook("evaluate", ...): it runs for allow and ask decisions, may change the effect to allow, ask or deny, and event.message is the denial reason. An explicit configured deny is final and never invokes the hook.

Treat an OpenCode plugin as code running with your privileges. Before relying on it, check your installed version’s docs for shell-hook configuration and an exit-code equivalent, and test whether throwing from a tool hook blocks a call. Test the whole setup with your local Ollama model too.

What a hook covers

  • A string match is easy to dodge. The example matches the literal string “drop table” in one command. A matcher selects by tool name only. If the model runs a script that contains the dangerous command, or spells it differently, a grep on the command text never sees it.
  • Hooks fire only on tool calls. PreToolUse fires when Claude calls a tool. A file added with an @ reference in your prompt is added to the conversation directly. A hook does not see it, and a Read deny rule may not stop it. Keep secrets out of the folder.
  • Hooks cannot override your deny and ask rules. A hook’s allow never overrides a deny or ask rule: those are still evaluated.
  • Hooks run with your full permissions. Command hooks “execute shell commands with your full user permissions”, so review and test them before adding them.

One checkpoint for high-stakes actions

If an agent can reach something with real-world consequences, such as ordering DNA synthesis or commanding physical equipment, put a screening checkpoint in the path that refuses dual-use requests (requests where the same capability can help or harm). Do not connect an agent to such a capability without one. Test the checkpoint with requests you know it should refuse. A hook is one possible checkpoint for local actions, with the limits listed above.

A hook in a repository is code you did not write

If a repository commits hooks in .claude/settings.json, they are code from its authors, running as you. Interactive Claude Code holds hooks back until you accept the workspace trust dialog.

In -p and SDK runs (headless: non-interactive, no one to answer a dialog) there is no dialog, and hooks committed in a repository’s .claude/settings.json run in a folder you have never trusted. Read .claude/ before running headless in a clone. --bare and disableAllHooks switch hooks off.

In a throwaway folder with mock files, add the Bash-blocking hook above and ask for a harmless command that contains “drop table” in an echo. Expect the agent to report that the command was blocked, with your stderr text as the reason. Then change the script to exit 1 and see what happens.
