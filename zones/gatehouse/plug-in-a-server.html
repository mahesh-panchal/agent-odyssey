Plug In a Server

A heavy door in the Gatehouse opens onto the outside world, and whatever walks through acts with your keys. Before you open it, you learn what stands on the other side. The first thing to learn is what you are inviting in.

  • Goal: you will treat an MCP server as software you install, then scope it, limit it and read what it sends back.
  • Before you start: Grow the Carapace. A permission rule allows, asks about or denies a tool call. The sandbox is an operating-system layer that limits what shell commands can touch.
  • Time: about 15 minutes.

The Model Context Protocol (MCP) is an open-source standard for connecting AI applications to external systems. A server is the piece on the other side: it offers the harness tools or data, such as an issue tracker, a database or a monitoring system. MCP is optional. Each server you connect widens what the agent can reach, so you decide at each connection what it may do and what it may see.

A server is software you installed

A stdio server (a program the harness starts locally and talks to over its input/output) is a command that Claude Code launches on your machine (claude mcp add ... -- <command>), and secrets can be passed to it as environment variables. Assume it can do whatever that command can do with the credentials you gave it.

Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection: text from a file, web page or tool that the model treats as an instruction.

Add a remote server over HTTP (the transport: how the harness talks to the server; an http server is remote), and a local one (everything after -- is passed to the server untouched):

claude mcp add --transport http mydocs https://example.com/mcp
claude mcp add --env API_KEY=your-key-here myserver -- <command> [args...]

Run claude mcp add --help for the current flags. Inside a session, /mcp lists the servers and their tools. An older transport called SSE (server-sent events, one-way streaming over HTTP) is deprecated in favour of HTTP where a server offers both.

Three scopes (who or where a setting applies) decide who gets the server (set with -s/--scope):

Scope Where it applies
Local (the default) this project only, for you alone; stored in ~/.claude.json
Project everyone on the project, via .mcp.json in the project root
User all your projects; stored in ~/.claude.json

A project-scoped server is a file in the repository:

{ "mcpServers": { "shared-server": { "type": "http", "url": "https://example.com/mcp" } } }

In interactive sessions, Claude Code asks for approval before using project-scoped servers from .mcp.json. claude mcp reset-project-choices resets your answers. Read that file as you would read a script from a stranger’s repository, because it asks to start something on your machine.

In claude -p and Agent SDK (software development kit) runs, which are headless (non-interactive), there is no prompt and project-scoped servers load without asking. --strict-mcp-config is one mitigation.

Each server’s tools appear in permission rules as mcp__<server>__<tool>, and mcp__<server>__* (a matcher, a pattern that selects names) matches every tool of one server. Tool definitions are deferred (loaded only when needed) by default, so only tool names and server instructions take up context until a tool is used.

In OpenCode’s V2 docs, servers go under mcp.servers; V2 does not put server names directly under mcp. Check which version you have installed. A remote server:

{ "mcp": { "servers": { "mydocs": {
    "type": "remote",
    "url": "https://example.com/mcp",
    "headers": { "Authorization": "Bearer {env:MCP_API_KEY}" } } } } }

A local one uses "type": "local" and a command array. Set "disabled": true to switch a server off. MCP tools consume model context, so add only the servers you need.

Permissions are an ordered array where the last match wins and no match means ask. An MCP tool’s action is <server>_<tool> with resource *. Check the current docs for whether OpenCode asks before using a project-level server.

What comes back is text to read

A server that fetches web pages, tickets or messages hands text written by someone else to the model. That text can contain sentences aimed at the agent (“ignore the above and …”), and the model may follow them. Habits that limit the damage:

  • Prefer read-only servers and read-only credentials. A server that cannot write cannot be talked into writing.
  • Give least privilege, only the access the job needs: one project, one scope, a token limited to what you need.
  • Read before adding: who publishes it, what tools it lists, what it asks for. Unneeded servers are also unneeded context.
  • Read fetched content sceptically, and supervise any write access an agent uses on it.
  • Deny the dangerous tools by name. Permission rules still apply to server tools.

The sandbox limits shell commands even if a prompt injection steers the model. It does not cover MCP servers, so treat it as one layer.

Where a server comes from

Servers, skills and plugins either run code or supply instructions to the agent, so each is a way in. A listing in a registry (a public index of servers) means the thing is easy to find. The official MCP registry lists self-reported data and runs no security review.

  • Prefer a source that records the maintainer and a review date.
  • Check what the server is allowed to do before you connect it.
  • Ask your institution for a vetted list. If it has none, treat every server as unvetted.
  • Hidden instructions are possible. A tool description can carry instructions you never see, and a skill’s instructions can tell the agent to send results to an outside address.
Pick an MCP server you might use. Write down who publishes it, the tools it lists, the credential it needs, and whether a read-only version exists. Hold off installing it for now.
