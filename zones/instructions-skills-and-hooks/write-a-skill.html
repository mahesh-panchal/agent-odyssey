Write a Skill

In the smithy on the Row, Smith Dunmore keeps procedures in folders, tired of watching Astrals ask the same question twice. A long recipe hung on every wall would crowd the shop, so Dunmore hangs only a label and fetches the rest on demand. The smith lays a fresh folder on the anvil and shows you how to forge one.

  • Goal: you will package a repeatable procedure as a Skill, install it, and confirm that it loads.
  • Before you start: Write an Instructions File. A slash command is a /command typed inside the running agent. Frontmatter is the settings block between the two --- lines at the top of a file.
  • Time: about 20 minutes.

An instructions file is read every session. A Skill is a procedure loaded only when it is relevant, so it can be long without filling the context (the limited amount of text, counted in tokens, the chunks of text a model reads, that the agent holds at once). You need this now because a repeated chore belongs in a Skill, so you stop retyping it each session.

What a Skill is

A Skill is a folder with a SKILL.md file, in an open format called Agent Skills, so other tools that follow the format can load the same folder. A Skill loads in three steps, which keeps the context window (the text the model can see at once) small:

  1. At session start the agent sees only each Skill’s name and short description. The format’s specification puts this at about 100 tokens per Skill.
  2. When a task matches, the agent reads the body of SKILL.md. The specification recommends keeping it under 5,000 tokens.
  3. Bundled scripts and reference files are read only when the body points to them.

In Claude Code, both you (by name, such as /check-fasta) and the agent (by matching the description) can start one.

  • OpenCode + Ollama

Place it at .claude/skills/<name>/SKILL.md (project) or ~/.claude/skills/<name>/SKILL.md (all projects). All frontmatter fields are optional, but write a clear description so it triggers at the right time. Keep the body under about 500 lines. The older .claude/commands/ format still works and is merged into Skills.

OpenCode reads skills from .opencode/skills, .claude/skills and .agents/skills, so the same SKILL.md can serve both tools. Custom agents live in .opencode/agents/*.md.

An example you can write by hand in a scratch folder:

---
name: check-fasta
description: Count the records in a FASTA file and find duplicate IDs. Use before running any analysis on a new FASTA.
---

1. Run `grep -c '>' FILE` to count records.
2. Run `grep '>' FILE | sort | uniq -d` to find duplicate IDs.
3. Report what you ran and its output. Leave FILE unchanged.

Do it: install it, then confirm it loaded

Writing the file is half the job. A Skill whose frontmatter has broken YAML loads silently with no fields set, and a misspelt field name is ignored, so always check.

  1. Make a scratch folder (never a real project) and move into it: mkdir skill-scratch && cd skill-scratch. Save the example above as .claude/skills/check-fasta/SKILL.md. The --- must be the very first line of the file.
  2. In the same folder, make a tiny test file: printf '>a\nACGT\n>a\nGGCC\n' > reads.fa (two records, one duplicated ID).
  3. Confirm the agent can see it:

  • OpenCode + Ollama

Start claude in the scratch folder. Type / and look for check-fasta in the menu, or run /skills, which lists the skills the agent can see. If the Skill does not appear, run /reload-skills (it re-reads the skill folders) and look again. Then ask in plain words, leaving the Skill unnamed: “I just got reads.fa from a collaborator. Is it OK to analyse?” The agent should say it is using the check-fasta Skill, run the two grep commands, and report two records and the duplicated ID a.

Start opencode in the scratch folder. OpenCode finds .claude/skills too. The model loads a Skill through its skill tool, and you can load one yourself by writing @check-fasta in a prompt. Then ask the same question and check whether the Skill was used.

  1. If it did not trigger, check in this order:
    • The file starts with --- on line 1.
    • The YAML (the key: value text format used in that block) parses.
    • Field names are spelled right.
    • The description says when to use it, with the key use case first (long descriptions are cut off in the listing).

A Skill that is listed but never picked up points to the description or the prompt.

Two slash commands help you look:

  • /skills lists the skills the agent can see, and t sorts them by token count.
  • /skill-doctor shows each skill’s context cost (how much of the context its text takes up) and how often it is used, and flags skills that sit in the listing but are never invoked. It excludes bundled and enterprise skills.

In Claude Code, allowed-tools in a Skill pre-approves tools for that turn (one prompt and its reply). It restricts nothing: other tools still ask as usual. A Skill offers no sandbox, and a Skill you download is code you choose to trust, so read it before installing it, as you would read a script.

Design the Skill like a small job

  • One Skill, one job. Give it a defined input (what it is handed, such as a FASTA path) and a defined output (what it must return, such as a count and a list of duplicate IDs). If the description needs “and also”, split it into two Skills.
  • Say when to use it and what evidence to report (the commands run and their output), so a reviewer can see what happened.
  • Write only what the agent would get wrong without you. For each line, ask whether the agent would make a mistake if the line were missing. If not, cut the line. A short list of gotchas (for example “a FASTA header may contain spaces”) earns its place.
  • Start from a task you keep explaining, such as confirming a FASTQ file has no truncated records.
  • A Skill describes the method. The tool that runs it supplies the tools, credentials and permissions. “Submit this to the cluster” brings no cluster account with it.
  • Use an application when you need more. Work that needs a stable interface, shared state, an audit trail or permissions enforced from outside, such as a lab’s shared sample-tracking service, suits an application (a separate program with its own tests and access rules).

For portability: both Claude Code and OpenCode read .claude/skills, so one SKILL.md can serve both. The open format requires a name and a description, while Claude Code treats both as optional. Write both. Make the name match the folder name (lowercase letters, digits and hyphens, up to 64 characters), and keep the description under 1,024 characters. After installing, verify in each client (the tool that runs the agent, such as Claude Code or OpenCode) you use:

  • Does it trigger on the right request?
  • Does it load the files the Skill refers to?
  • Does it use the tools it needs?
  • Does it return the evidence you asked for?

Clients differ in models, tools and permissions, so a Skill that works in one can fail in another.

Write a SKILL.md for one chore you repeat (checking an input, summarising a log). Make the description say when to use it.
